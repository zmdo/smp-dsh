## 1. 已确认的需求

| 事项 | 已确认规则 |
| --- | --- |
| 国际化 | 服务器管理响应平台语言设置，至少完整支持当前平台的中文、英文 |
| 默认类型 | 新登记的服务器默认选「空置服务器」；另一内置类型是「普通服务器」 |
| 空置服务器 | 没有任何必要软件，不自动安装 Docker、Compose 或其他软件 |
| 普通服务器 | 必要软件是当前已有的 Docker Engine 和 Docker Compose |
| 类型与软件 | 必要软件随类型变化，不再是全部服务器共用一份可随意勾选的安装清单 |
| 系统分组 | 允许插件注册；这类分组不可删除，必须提供国际化名称 |
| 自定义类型 | 系统分组可提供自己的类型列表和必要软件；没有提供时使用内置类型列表 |
| 软件扩展 | 插件可以提供 Docker、Compose 之外的软件，以及相应检测和安装脚本 |
| 移动时选类型 | 弹窗选择目标类型；能够保留同一有效类型时预选原类型，否则预选目标分组默认类型 |
| 自动安装 | 保留自动安装开关，不改成登记或移动时无条件安装 |
| 软件冲突 | 例如已安装版本与目标要求不一致时，先询问是否替换；拒绝替换则取消此次移动 |
| 移动完成时机 | 需要执行安装或替换时，软件处理成功后才更新分组和类型 |
| 失败处理 | 软件处理失败时保留原分组和类型，并报告远端实际变化；不能声称远端修改已被数据库回滚 |
| 版本范围 | 支持不限定、完整固定版本、最小版本、最小至最大版本区间，以及大小版本系列 |
| 版本系列 | `27` 表示 `27.x.x`，`27.3` 表示 `27.3.x`；完整固定版本 `27.3.1` 才锁定一个版本 |
| 范围配置 | 类型／插件定义允许范围，登记和编辑服务器时可进一步收紧，不能突破类型要求 |
| 自动检测升级 | 登记和编辑时按每个软件单独选择，默认关闭；只检测并生成升级建议，不直接安装或升级 |
| 检测限制 | 固定版本和已达完整上限的软件没有范围内的更高候选；只是当前已是最新版本时继续保留检测策略 |
| 升级确认 | 所有版本升级均需明确确认，小版本和补丁也不再自动执行；跨大版本在确认计划中明确标识 |
| 推迟 | 只延后提醒，到期重新展示建议，不到时自动升级；确认安排升级才会执行 |
| 拒绝本次 | 只拒绝这台服务器上该软件的这个目标版本，不反复提醒；可撤销，更高版本仍可继续检测和提醒 |
| 批量安排 | 可筛选需要升级的服务器，选定清单，统一安排时间及同一软件的目标版本 |
| 升级管理界面 | 侧栏「服务器管理」分组下提供「服务器实例」「服务器密钥」「升级管理」入口；升级管理内以三个 Tab 展示建议、计划和执行记录 |
| 批量失败 | 一台失败时暂停尚未开始的服务器；已经开始的任务有序结束并报告实际结果 |
| 调度方式 | 控制端统一调度，通过 SSH 操作；接受控制端停机时暂停检测，恢复后补一次检查。预约错过时间的处理建议见第 12.7 节 |

本轮不实现会话工具，也不改变会话权限。本文的服务器分组与「工作区组」是两套概念，不建立隐含的绑定关系。

## 3. 国际化范围与建议

### 3.1 页面随平台语言更新

建议复用本项目已有的 `locale` 服务和页面订阅方式：

- 栏目标题、服务器和密钥页签使用读取当前语言的标签函数；`groupLabel` 也支持函数。壳已经支持这种形式，无需替换侧栏。
- 服务器列表、分组栏、登记与编辑、详情、终端提示、密钥页面、新增升级管理 Tab 及其建议、计划、执行记录、分页、加载和空态全部使用中英文本。
- 软件名称、说明、服务器类型名称、系统分组名称也由当前语言解析。
- 日期按平台所选语言格式化，状态与枚举用翻译表显示，不直接展示内部值。
- 切换语言不重置当前分组、搜索词、页码、表单输入和所选类型。
- 初期覆盖 `zh`、`en`，其他语言回退英文。用户输入的服务器名、普通分组名、密钥名保持原文。

插件介绍的 `meta` 与页面文字是两个层次，都需要维护。系统分组和类型的标识不使用翻译后的名称，切换语言不能生成新记录或改变归属。

### 3.2 宿主错误和任务结果

建议宿主返回稳定的错误码和必要参数，页面按当前语言显示。不能通过匹配中文 `detail` 来推断错误类型。

新的任务摘要可记录结构化的事件码和参数，让页面在查看时翻译；服务器脚本的原始输出、第三方错误和已有任务摘录保留原文。国际化不意味着改写远端命令输出，也不要求重译历史日志。

软件探测结果必须有结构化字段；机器判断使用状态、软件标识和版本，不使用翻译后的描述。

### 3.3 国际化阶段实施进展

现有服务器与密钥页面已接入平台语言服务，其他语言回退英文。覆盖栏目、页签、分组虚拟项、列表、分页、登记、编辑、详情、终端提示、密钥表单、内置软件说明，以及可达、容器和任务状态。表单及接口错误按稳定代码翻译，已经显示的错误和成功提示也随语言切换；中英虚拟分组名均受创建校验保护。

服务器名、用户分组名、密钥名、区域等登记数据和原始脚本输出、任务摘录不按中文内容匹配翻译。插件自定义类型、软件和系统分组的国际化元数据随对应功能实现；新的结构化任务摘要仍是后续扩展，不把现有日志改写为译文。

验证包括插件构建、14 项测试、CES 实例内的平台语言切换及接口错误显示，并通过隔离的 React 状态检查确认分页、搜索、未提交的服务器与密钥表单、已显示错误在语言切换后保留，语言切换不重复请求初始化数据，卸载会清理订阅。本阶段未修改数据库结构，临时插件保持禁用。

## 4. 分组、类型与必要软件的关系

建议以这一条关系作为后端规则来源：

> 分组决定可选类型和默认类型；类型决定必要软件及版本要求；服务器保存所处分组与所选类型；实际安装情况通过检测取得。

### 4.1 内置类型

下列内置标识已实现。

| 类型标识 | 中文 | 英文建议 | 必要软件 | 默认 |
| --- | --- | --- | --- | --- |
| `builtin/vacant` | 空置服务器 | Vacant server | 空集合 | 是 |
| `builtin/general` | 普通服务器 | General-purpose server | Docker Engine、Docker Compose，Compose 依赖 Docker | 否 |

普通分组、未分组，以及没有声明类型列表的系统分组使用这两种类型。普通类型暂不增加用户未要求的固定版本：保留现有可用版本即可，不能把任意版本差异都当作冲突。

「空置」表示没有必要软件，不表示必须卸载已经安装的软件。普通服务器改为空置服务器时，不自动卸载 Docker、Compose 或清理容器。

### 4.2 插件提供的类型

建议规则：

- 插件没有声明类型列表时，使用完整的内置列表及默认类型。
- 插件声明了类型列表时，该列表替换内置列表，不再偷偷追加空置或普通类型。
- 自定义列表必须非空、标识不重复、提供中英名称，并明确一个有效的默认类型。显式空列表是配置错误，与“未提供”不同。
- 类型所需的软件、版本和依赖必须能够解析；缺少组件、依赖成环、默认类型不存在等错误在插件注册时明确报告。
- 类型采用稳定且有命名空间的标识。同名显示文字不代表同一类型，不同插件不能靠碰巧同名互相覆盖。
- 移入新分组时，只有目标确实支持原类型及其有效定义时才保留它；不能只比较显示名称。
- 插件更新后如果移除了已有服务器所用的类型，显示“类型定义不可用”，保留原类型记录并要求显式转换，不能悄悄改成默认类型。

登记表单在选择分组或类型后立即更新必要软件列表，明确展示软件名、版本要求及是否需要安装。必要项由类型决定，不允许通过取消某个必要项的勾选来绕过类型要求。

自动安装开关只控制缺失软件的安装时机，不改变必要软件集合，也不构成对任意版本替换的长期许可。自动检测升级另有逐软件开关，默认关闭；开启后只持续检测并生成建议，实际升级仍须确认，详见第 12 节。

## 5. 插件系统分组

### 5.1 身份与保护

已由服务器管理插件提供 `serverManagement` 宿主服务，其他 Cordis 插件通过依赖注入调用 `registerDefinitions()` 注册系统分组；当前契约与示例见 [执行基础实施记录](execution-foundation.md)。

注册内容至少包括稳定分组键、中英名称、排序值，以及可选的类型列表、默认类型和软件定义。分组身份由插件身份与稳定键共同确定，数据库中的分组 UUID 在重启和插件重新加载后保持稳定。

普通用户创建的分组仍是用户分组。浏览器和未来会话工具不能通过提交 `kind=system` 等字段伪造系统身份。

系统分组不可删除必须同时落实在页面与宿主接口：侧栏不提供删除操作，直接调用删除接口也拒绝。不能只隐藏按钮。插件更新分组标题时不改 UUID，不影响已有服务器。

普通分组继续遵循名称唯一的规则。系统分组不能用翻译文字作为唯一标识；其身份唯一性、展示名称和普通分组的名称唯一性需要分别处理。界面遇到重复显示名称时可展示插件来源以区分。

「全部服务器」与「未分组」是内置虚拟项，不是插件注册的实体分组。建议保留它们的中英名称，避免普通分组在切换语言后与这些入口混淆。

### 5.2 生命周期建议

插件注册应由 Cordis 生命周期管理，不使用模块级可变注册表：

- 插件卸载时停止接受依赖其定义的新登记、移入和软件变更，清理注册与订阅；已经使用其脚本的任务须先结束或明确取消，再释放执行资源。
- 分组数据库记录、服务器归属和已安装软件不随插件卸载删除。建议保留一个“所属插件未启用”的系统分组展示，禁止新服务器移入；原服务器仍可移出。
- 缓存的名称和类型摘要可用于解释现状，不作为插件卸载后继续执行安装脚本的依据。
- 插件重新启用时按稳定键恢复同一分组。定义变化后重新判断软件符合状态，不因为插件更新自动升级或降级远端软件。
- 已有登录、终端和指标功能不因失去某个类型定义而被误判为服务器不存在。

注册、停用、缓存展示和任务释放已按上述规则实现。涉及不同必要软件的移出仍受第 13 节的阶段限制；插件卸载不会重写或删除服务器。

## 6. 软件检测、版本和安装能力

### 6.1 软件与安装配方分开

同一种软件在不同分组可能要求不同版本。建议区分：

- 软件标识：表示机器上的同一软件，例如 Docker Engine。用于跨分组比较，不能因插件不同就把两份互相覆盖的软件当成无关项。
- 安装配方：由某个插件或内置组件提供的检测、安装、替换实现，有自己的稳定标识和修订信息。
- 类型要求：引用软件、版本约束和所用配方。
- 实际状态：本次检测到的软件版本、可用性和检测时间。

版本要求按本次补充需求支持不限定、精确版本、最小版本、闭区间和版本系列，详见第 12.1 节；不再采用初稿中仅支持两种要求的建议。不同软件仍需明确版本解析和比较规则，不同配方的兼容性由元数据决定，不能仅靠软件名猜测。

### 6.2 预检的分类

| 检测情况 | 处理建议 |
| --- | --- |
| 已安装且满足要求 | 保留，不重新安装 |
| 未安装 | 列入缺失项，按本次安装选择决定是否安装 |
| 已安装但版本或配方不兼容 | 列为冲突，展示当前与目标，必须明确询问是否替换 |
| 无法判断、权限不足或检测失败 | 标为未知并说明原因，不能宣称缺失或无冲突 |
| 需要替换，但配方不支持目标版本或替换 | 明确阻止该操作，不把普通安装脚本当作替换脚本使用 |

版本的当前值必须来自远端检测，不能只比较原分组与目标分组的声明。没有版本要求的类型不应因为检测到的版本与安装源当前版本不同而提示替换。

本节针对登记、移动和必要软件准备。“已满足要求则保留”不排除继续检测新版本并人工安排升级。已经满足类型要求的软件，不因后续检测到新版本而直接修改远端安装。

### 6.3 组件契约需要扩展

当前 `component.json` 加两份 shell 脚本不足以支持这些规则。建议补充软件身份、国际化名称、结构化检测结果、版本比较器、可安装版本枚举、精确目标包解析、依赖，以及安装、升级和替换能力。

插件可以提供自己的脚本，但脚本必须随已加载的宿主插件注册，不能由页面请求提交任意脚本路径。安装、替换完成后都要重新检测，确认实际版本满足要求，不能只凭安装脚本退出码为 0 就算完成。

现有 Docker、Compose 脚本需要适配新契约。它们目前只安装缺失软件、跳过已安装软件，不具备固定版本替换功能。必要依赖必须纳入同一计划，检测出相互矛盾的版本要求时先报错，不尝试按顺序覆盖。

## 7. 登记、编辑和移动流程

### 7.1 登记与编辑

登记时根据所选分组取得类型列表，默认类型按第 4 节确定，必要软件区域同步更新。编辑已有服务器时显示其真实类型，不因为打开表单就重置为空置类型。

建议将“仅保存登记”与“安装必要软件”分开解释：

- 自动安装关闭时可以只保存登记，缺失必要软件显示“待安装”；不能显示成已满足要求。
- 自动安装打开时，在执行之前预检；已满足的保留，缺失的按所选类型安装，冲突的单独询问。新登记也可能遇到已安装软件，因此不能只在移动时处理冲突。
- 空置类型没有安装任务，不运行 Docker、Compose 安装脚本。
- 编辑中改变分组或类型时走与移动相同的规则，不能通过普通 `PATCH` 绕过预检和确认。
- “安装必要软件”按钮只处理当前类型的必要项，不能继续安装全局目录中的所有组件。
- 每项软件同时展示类型允许范围、服务器进一步收紧后的有效范围、自动检测升级开关及建议处理状态。固定版本、已达上限、配方不支持等情况分别说明；不能把所有情况都写成“没有新版本”。

这些安装时机的细节是按“保留自动安装开关”推导的建议；缺软件时允许仅保存登记，不意味着可以跳过已经发现的版本冲突提示。

### 7.2 移动服务器

当前行末的分组选择框不能再直接发出只含 `group_id` 的修改请求。建议改为发起移动弹窗，过程如下：

1. 选择目标分组，加载其类型列表；预选同一有效类型，否则预选目标默认类型，允许用户调整。
2. 服务端解析目标要求，检查服务器和目标定义，必要时通过 SSH 只读预检实际软件。已有主机指纹按现有规则校验。
3. 展示当前分组、类型，目标分组、类型，以及保留、缺失、安装、替换的软件。检测不成功时明确显示未知，不能给出虚假的“无冲突”。
4. 发生冲突时明确询问是否按列出的计划替换。拒绝或取消则结束此次移动，分组、类型和远端软件均不因这次操作改变。
5. 确认之后重新校验记录和定义。需要安装或替换时入队执行，等待成功验证后，再用数据库事务同时更新分组和类型。
6. 安装或替换失败时，分组与类型保留原值；任务报告已经发生的远端变化、失败环节和实际检测结果。不得把数据库未更新说成远端也没有变化。

按保留自动安装开关的规则，关闭自动安装、且只是缺少软件时，建议允许仅移动并标为“待安装”。对于已发现的冲突仍必须询问；用户明确同意的替换只授权本次计划中的动作，不自动打开之后的自动安装，也不授权未来未知版本的替换。

改为空置类型或不再需要某项软件时，默认保留现有软件。删除普通分组后服务器回到未分组，也必须保证其类型在默认类型列表中有效；用户分组本身只使用内置类型，系统分组不可删除，因此不能借删除分组跳过自定义类型转换。

### 7.3 预检与执行之间的变化

建议给计划绑定服务器配置修订、源与目标分组和类型、插件规则修订、检测到的软件状态以及用户确认的具体替换项。计划仅对这次操作有效。

配置修订不能直接使用现有 `updated_at`：巡检和组件状态更新也会修改它。指标或巡检刷新不应让人的确认无故失效；地址、凭据、分组、类型或必要软件规则变化则应使旧计划失效。

用户考虑确认时不持有数据库事务或远程 SSH 连接。执行前如果发现软件版本、目标定义或服务器配置已经改变，就要求重新预检，不能把旧确认扩大成任意替换许可。

需要远端操作的移动沿用同一服务器任务串行的规则，并防止同期编辑或移动覆盖源记录。分组和类型更新须使用预期配置修订进行条件写入。执行已开始后发生了无法避免的外部变化时，保留实际结果并报告，不能强行覆盖新的登记信息。

## 8. 空置类型对现有运行逻辑的影响

这是本次需求不能遗漏的部分：

- SSH 连接成功与必要软件是否满足是两个状态。空置服务器不应因为没有 Docker、Compose 而被标成连接失败。
- 连接测试保留认证、主机指纹等检查；软件检测改为根据类型执行，安装则根据开关和本次确认计划执行。
- 巡检不再对所有服务器强制运行 Docker 命令。没有 Docker 时不运行容器巡检，不将未安装解释为空置服务器故障。
- 空置服务器如果本来装有 Docker，可以展示实际检测结果，但不得据此把 Docker 变成其必要软件。
- CPU、内存、磁盘采样不依赖 Docker，应继续独立工作。
- 容器数据必须说明是否已检测、检测时间及是否过期；不能把没有执行容器巡检解释成已经确认机器上没有容器。
- 定时巡检与自动检测升级不安装、升级或降级软件。实际升级由用户确认的即时或预约计划执行；自动安装开关不能替代这种确认。

底层分别保存连接、必要软件符合情况和任务阶段；实例列表按新的 [列表设计](server-instances-list.md) 聚合成一个「状态」列，详情仍能查看各项事实与原因。

## 9. 数据、接口与任务的改动范围

以下是建议的逻辑模型，具体列名、接口名和迁移编号在实现前确定。

| 对象 | 需要补充的内容 |
| --- | --- |
| 服务器分组 | 用户或系统来源、插件身份与稳定键、国际化定义、定义修订与当前可用状态 |
| 类型与组件注册 | 稳定类型键、默认类型、国际化名称、必要软件与版本要求、依赖与配方归属 |
| 服务器 | 稳定类型键、配置修订、必要软件实际状态；分组和类型必须成对校验、更新 |
| 准备任务 | 目标分组与类型、源配置修订、具体安装或替换计划、一次性确认范围、分步骤结果 |
| 分组及服务器接口 | 返回国际化展示信息、类型选项、默认类型、系统分组删除能力和软件符合状态 |
| 错误及任务摘要 | 稳定代码与参数，原始远端输出单独保留 |
| 逐软件检测策略 | 用户收紧的版本约束、自动检测开关、下次检查时间及规则修订；不包含持续执行升级的许可 |
| 升级建议与处理 | 服务器、软件及候选版本，推迟提醒时间、拒绝记录及撤销状态、检测时间和失效原因 |
| 批量计划与执行 | 固定服务器清单、统一目标软件版本、各机器精确包与依赖计划、确认记录、执行时间、并发及失败暂停规则、父子任务结果 |

前端只负责选择与展示，宿主统一解析有效类型、必要软件和有效版本范围。直接调用旧 `PATCH`、手动安装、自动安装、已确认的升级计划和未来的会话工具，都不能绕过同一套规则；检测任务不能调用软件变更入口。

普通分组名、系统稳定键和翻译文字的唯一性规则需要在数据约束中分别落实，不能继续把所有分组都当作一个唯一的中文 `name`。

用户已确认当前无服务器数据、无发布部署，允许破坏兼容性的更新。后续可重整服务器模块建表及接口，取消旧服务器回填和旧字段兼容，新登记默认空置。初始化及相关空表重建方式需与迁移执行记录一并设计；具体问题与范围见 [数据库重构建议](database-redesign.md)。第 13 节记载的旧回填属于已经完成阶段的历史行为，不再约束后续结构。

## 10. 与后续会话功能的衔接

[session-catalog.md](session-catalog.md) 目前将移动定义为“只改 `group_id`”，并允许可视服务器被移动。这与新需求中的类型转换和软件替换已不再等价。

后续实现 `server_move` 时需要同步修订设计：

- 纯登记信息变化可以继续讨论使用 `visible` 权限，但涉及远端安装、替换时，不能通过可视权限间接取得服务器操作能力。
- 建议初期需要远端软件修改的移动只在控制台完成；将来开放给会话时至少需要 `operate`，并把具体目标类型及软件计划纳入原生批准。
- 插件注册的系统分组与会话创建的用户分组区分来源，会话创建工具不能成为注册系统分组的入口。
- 会话工具也不能绕过系统分组删除保护、目标类型校验和冲突处理。

本轮不据此提前开发 `server_list`、`server_shell` 或目录修改工具。

## 11. 建议实施顺序与验收

建议顺序：

1. 先完成服务器管理现有页面与宿主错误的中英国际化；新增升级管理 Tab 时同步提供完整中英文。
2. 建立分组、类型和软件定义的统一解析，以及系统分组注册与保护。
3. 加入内置类型，修正连接测试、巡检和安装对 Docker 的全局依赖。
4. 建立预检、冲突确认、按计划执行和成功后提交移动的流程，接入插件软件。
5. 在现有左右布局中加入类型选择、必要软件展示及移动弹窗，不重做全局侧栏。
6. 在前述版本解析与执行能力上加入逐软件自动检测，新增独立「升级管理」Tab，集中承载建议处理、批量预检与确认安排、计划调度和执行结果；实例页保留状态、筛选与跳转入口，检测与执行使用明确分开的入口。

验收至少覆盖：

- 平台切换中英文后，栏目、服务器与密钥页面、系统分组、类型、软件说明和提示立即更新，当前输入和分页不丢失。
- 默认登记为空置类型，不安装任何软件；没有 Docker 的服务器仍能完成 SSH 连接测试并采集主机指标。
- 普通类型只要求 Docker 与 Compose，安装动作按依赖顺序执行，不安装不相关的软件。
- 插件未提供类型时使用内置列表；提供时完整替换，错误定义明确失败。
- 系统分组从页面、接口均不可删除；重启、切换语言和重新加载插件不会改变分组身份。
- 插件可增加一种 Docker、Compose 之外的软件；注册、检测、安装与卸载生命周期完整。
- 移动时正确预选并校验目标类型；无软件变化的移动不无故触发安装。
- 缺失、版本冲突、权限不足和检测失败可区分；拒绝替换没有远端或分组副作用。
- 软件处理成功后才提交分组和类型；部分失败能报告实际变化，不伪造远端回滚。
- 预检后修改服务器配置、插件规则或实际软件版本，旧计划不能继续执行任意替换。
- 关闭自动安装时的待安装状态正确；确认一次替换不会变成永久自动替换。
- 编辑、直接接口调用和手动安装都不能绕过类型规则；既有分组侧栏、搜索、分页和密钥保护继续有效。
- 版本范围、自动检测及批量升级的专门验收见第 12.10 节。

实现阶段先用脚本执行替身和隔离数据验证计划与失败路径；真实软件升级或替换应使用专门的测试服务器，不用已有业务机器验证破坏性流程。

## 12. 版本范围、自动检测升级与批量安排：补充分析

本节按最新需求修订：自动检测与人工执行分开，所有升级均需确认。此前“范围内的小版本与补丁自动执行”的方案已被本轮需求替代；版本范围、逐软件设置、默认关闭和控制端统一调度的规则保留。推迟、拒绝与批量失败行为已向用户确认；下文标为建议的计划细节不代表功能已经实现。

### 12.1 版本范围的准确含义

建议页面以明确的模式和输入框表达版本要求，后端存储结构化条件及精度，不把含糊的文字直接拼成安装命令。以下版本号仅用于说明语义，不是推荐安装的软件版本。

| 模式 | 示例 | 匹配含义（稳定版本） | 可形成的升级建议 |
| --- | --- | --- | --- |
| 不额外限定 | 不填写 | 不额外缩小类型／插件允许的集合 | 有效范围内的更高版本 |
| 固定版本 | `27.3.1` | 仅该软件版本 | 已满足固定版本时无升级候选 |
| 大版本系列 | `27` | `>=27.0.0` 且 `<28.0.0` | 该系列内的更高版本，执行仍需确认 |
| 小版本系列 | `27.3` | `>=27.3.0` 且 `<27.4.0` | 该系列内的更高补丁，执行仍需确认 |
| 最小版本 | `27.3` | `>=27.3.0`，本条件没有上界 | 范围内的更高版本，跨大版本明确标识 |
| 最小版本 | `27.3.1` | `>=27.3.1` | 同上 |
| 最小至最大 | `[27.3.1, 28.0.2]` | `>=27.3.1` 且 `<=28.0.2` | 未达上界时可检测出更高版本 |
| 带系列上界的区间 | `[27.3, 28.1]` | `>=27.3.0` 且 `<28.2.0`，包含整个 `28.1.x` 系列 | 不能把 `28.1.0` 当成系列最高版本 |

固定模式要求完整版本号；只输入 `27` 或 `27.3` 应引导到版本系列模式，不能自动补成一个固定的 `.0` 版本。区间下界缺少的段补零，上界缺少的段表示包含该上界系列。建议复用成熟版本范围库的展开规则，避免自行按字符串排序；上述展开方式与 [node-semver 的范围说明](https://github.com/npm/node-semver#advanced-range-syntax) 一致。

需要拒绝无效版本、空交集及颠倒的上下界；`[27.3.1,27.3.1]` 的有效集合只有一个版本，没有范围内的更高版本。`[27.3,27.3]` 则代表整个 `27.3.x` 系列，两者不可混为一谈。

### 12.2 插件范围、用户范围与实际安装包

类型／插件范围是硬性边界。用户未收紧时继承它；登记和编辑中的选择只能进一步收紧。宿主计算两者交集作为有效范围，并验证用户选择，不能信任前端已禁用的选项。空交集拒绝保存；越过类型边界的输入不能被当成新的安装权限。“不限定”在页面上应明确写成“不额外限制，仍遵循类型要求”。

软件版本与系统安装包版本需要分开保存。例如 Debian 包版本可能含 epoch 和发行包修订，比较规则也不同，不能简单删掉这些内容后当作完整包版本。[Debian 版本格式与比较规则](https://www.debian.org/doc/debian-policy/ch-controlfields.html#version) 明确区分这些部分。

建议软件适配器负责以下转换：

1. 从目标服务器和指定可信安装源取得实际可安装的版本与包，不用网站上最新发布号代替可安装版本。
2. 把软件版本规范化，用于满足用户看到的大小版本条件；同时保留原始包版本和包管理器比较结果。
3. 根据有效范围、机器系统与架构、依赖兼容性解析一个具体安装计划，列出精确包版本。
4. 安装或升级执行该计划，而不是执行无约束的“安装最新版”或整机 `apt upgrade`。

定义是否合法与目标机此刻能否安装是两项检查。插件注册校验版本语法和依赖定义，不要求所有服务器在线；安装源暂时不可达也不能让整个系统分组被当作未注册。

Docker 的官方安装说明本身也要求先列出源中的可用版本，再选择具体版本安装，说明固定软件版本必须落实到真实包版本，而不能只改页面展示。[Docker 指定版本安装](https://docs.docker.com/engine/install/ubuntu/)。

对于采用语义化版本的软件，按数字比较大、小、补丁段，不能把 `27.10` 排在 `27.9` 之前。非语义化版本的软件由适配器提供规则，不能使用宽松转换把未知字符串硬凑成数字。建议默认只检测稳定版本候选；预发布版本不因数值更大就自动纳入。[SemVer 规范](https://semver.org/spec/v2.0.0.html)、[node-semver 的预发布规则](https://github.com/npm/node-semver#prerelease-tags)。

### 12.3 自动检测与执行分别处理

| 行为 | 含义 | 设置或确认来源 |
| --- | --- | --- |
| 自动安装 | 为选定类型补齐尚未安装的必要软件 | 现有自动安装开关；不授权之后的版本升级 |
| 一次替换 | 为登记、编辑或移动解决已发现的版本／配方冲突，可能包含降级 | 本次预检计划的明确确认 |
| 自动检测升级 | 检测已安装版本、可安装候选及约束，保存结果与升级建议 | 每个软件独立的检测开关，默认关闭 |
| 执行升级 | 按确认的服务器、具体版本及时间执行一次计划 | 用户明确选择立即升级，或确认安排升级 |

自动检测只产生信息，不安装、升级、降级软件或重启服务，也不直接创建可执行的升级任务。不能把范围内的小版本或补丁当成默认已获执行许可。手动“立即检测”遵守同样的边界，即使周期检测关闭也可以主动检查。

尚未安装的软件显示“待安装”，不能把首装伪装成升级建议。自动安装与检测开关互不代替；在登记、编辑中开启检测，不构成对任何一次升级的确认。

类型、分组、用户范围和插件规则变化后重新判断。新增软件的检测开关默认关闭；已安装版本变成不合规时显示冲突，不通过后台升级或降级自动修复。受影响的旧建议重新计算，已确认计划按第 12.7 节复核。

### 12.4 最高版本、当前最新与候选选择

| 情况 | 检测与展示行为 |
| --- | --- |
| 已满足完整固定版本，或有效范围只含一个版本 | 没有范围内的更高候选，检测选项不可用并说明原因 |
| 当前恰好达到完整、可包含的版本上界 | 显示“已达允许上限”，停止无意义的周期候选检查，保留用户设置供规则变化后重新判断 |
| 当前只是安装源中最新的合规版本 | 保留已开启的检测，等待未来发布的新版本 |
| 上界是 `28.1` 这样的系列 | 不把 `28.1.0` 当成最高版本，未来 `28.1.x` 仍可能成为候选 |
| 同一大版本内有更新，也存在更高大版本 | 分别展示同系列与跨大版本候选，任何一个都须确认后执行 |
| 源不可达、版本不可解析或依赖无解 | 显示检测失败或候选不可安装的原因，不伪装成“已是最新” |

建议先获取实际可安装版本，过滤有效范围与依赖，再列出高于当前版本的候选。比如当前为 `27.2.0`，源中有 `27.3.0` 与 `28.0.0`，范围不限时可以同时建议两条路径，默认突出同大版本的更新，并明确标识跨大版本影响；两条路径均不自动执行。

“有新版本”“需要升级”“不符合类型要求”需要区分。前者是检测事实，升级建议还要考虑约束、可安装性和用户处理状态；当前版本不符合要求则另外显示冲突，不靠把它隐藏为“无升级”来掩盖。

范围限定哪些版本可用，不保证源里一定存在。指定版本不可安装时明确报告，不回退到范围外或另一个未确认版本。普通升级目标须高于实际安装版本；降级、重装、切换来源和配方沿用单独的替换确认流程。

### 12.5 推迟提醒与拒绝本次目标版本

用户已确认两种操作均不执行软件变更，也不关闭后续版本检测。

| 操作 | 已确认含义 | 建议补充的界面行为 |
| --- | --- | --- |
| 推迟升级 | 指定时间后重新提醒，到时不执行升级 | 操作文案使用“稍后提醒”，展示恢复提醒时间；允许提前恢复 |
| 拒绝本次升级 | 只拒绝这台服务器上该软件的这个目标版本，不重复提醒；可撤销 | 展示已拒绝版本及撤销入口，更高目标仍可形成新提醒 |
| 安排升级 | 明确确认目标版本和时间后，才形成可执行计划 | 与“稍后提醒”使用独立入口，确认页明确时间含义 |

建议推迟按“服务器＋软件”保存提醒截止时间。期间继续检测并更新可见结果，新的候选也等到截止时间再主动提醒，用户仍可主动查看、选择升级；到期只恢复提醒，不把建议转成任务。这个推迟粒度是建议，区别于已经确认的拒绝粒度。

拒绝记录按“服务器＋软件稳定标识＋目标版本身份”去重，不使用每次检测新生成的记录 ID 或检测时间作为身份，避免同一版本反复提醒。版本适配器须保留有意义的包修订；相同软件版本的等价版本字符串不能绕过拒绝。拒绝某个目标后，不把它自动换成另一个较低候选继续催促；将来更高版本仍正常提醒。

建议和处理状态持久化，页面刷新、控制端重启、切换语言后仍有效。撤销拒绝后重新校验候选；已经不可安装或被新规则排除的版本不能因为撤销而变得可执行。拒绝不永久禁用软件检测、不放宽版本要求，也不取消类型冲突提示。

已安排的升级有独立的取消和改期入口。建议对已有计划的同一软件明确展示“已安排”，引导用户修改或取消计划；不能让“推迟提醒”看起来已经推迟了执行，也不能让拒绝一条建议冒充取消了已安排任务。正在修改软件的任务按第 12.7 节有序处理。

### 12.6 筛选服务器与统一安排升级

在现有服务器实例列表保留升级状态、“需要升级”筛选及跳转入口，保留分组侧栏、定高和分页。批量选择、预检、推迟、拒绝与安排等操作集中在独立的「升级管理」Tab，具体职责见第 12.8 节。

升级管理中建议结合分组、类型、软件、当前版本、目标版本、可达状态及处理状态筛选；可另看已推迟、已拒绝、检测失败和已安排的记录，不能把这些情况都混成“没有更新”。支持跨分组筛选与统一安排，服务器数量按机器去重，同时显示涉及的软件项数。

跨页选择需明确区分“当前页”与“全部筛选结果”。确认时固定服务器 ID 清单，之后新加入分组或新符合筛选的机器不能自动进入旧计划。预检发现不可执行项时逐项列出原因及数量，要求明确调整清单，不能静默少升级几台。主动纳入已推迟或已拒绝的建议时应显示该状态，并由本次确认明确覆盖本次选择。

“统一版本”的建议定义如下：

- 针对同一种软件，选择一个明确的软件版本，所有入选服务器必须都允许且实际可安装该版本。按各服务器的插件范围、用户收紧范围、系统、架构及依赖取交集，不能只看其中一台。
- 各发行版的原始包版本、架构和包文件可以不同，但适配器必须验证它们对应同一个确认的软件版本，并在计划里记录各自的精确包版本。
- 没有共同可用版本时，提示排除阻塞机器或拆分批次；不能把“统一版本”变成各台机器分别安装自己的最新版。
- 多种软件各有自己的统一目标，例如 Docker 与 Compose 分别选版本，不要求二者版本号相同。依赖软件的任何变化也列入同一确认计划。
- 已达到或超过目标版本的机器不执行重复安装或降级，预检中明确列出并调整清单；需要降级的另走替换流程。

建议批量操作分为“选择服务器 → 选择软件及共同目标 → 预检 → 确认立即执行或安排时间”。确认页至少展示：固定机器清单、各机当前与目标版本、精确包和依赖变化、跨大版本标识、服务重启与健康检查、执行时间及时区、允许启动的维护窗口、并发数量和失败暂停行为。未知影响明确显示未知，不展示无依据的“无中断”。

“统一安排时间”表示一次计划在确认的窗口内调度，不要求所有机器同时重启。建议默认串行，先验证一台再继续，并允许在确认时配置受控并发；具体默认参数留待实施确定。窗口约束任务启动，已开始的包处理与验证需要有序结束，不能承诺业务影响必定在窗口终点前结束。

用户确认的是这份具体计划，不是“到时升级到最新”。后来发布新版本不改变目标，后台筛选变化不增加机器，执行前状态变化按第 12.7 节处理。

用户已确认批量失败行为：任一服务器升级或升级后验证失败，暂停其余未开始的服务器；已经开始的任务继续完成必要步骤和验证。调度器与执行者须在真正开始远端变更前共同检查暂停状态，避免已领取但未执行的任务继续启动。失败后展示每台实际结果，恢复、重试或另约时间均需显式操作并重新预检；成功机器不重复升级，也不把跨机器的部分成功说成整体回滚。

### 12.7 控制端检测与执行调度

已确认采用控制端统一调度，通过 SSH 操作目标机。目标机不另设常驻 cron 或 timer；插件在自身 Cordis 生命周期内管理检测调度与已确认计划。已有队列可复用，但当前代码尚无本节的候选、建议处理和批量计划能力。

检测与执行保持两条流程：

1. 检测到期或用户主动检测 → 校验定义与服务器状态 → 检测实际版本和安装源 → 解析候选 → 保存结果、去重及处理提醒。流程在生成建议处结束，不能进入软件变更队列。
2. 用户确认即时或预约计划 → 保存清单、精确版本、配置与规则修订、确认记录和时间窗口 → 到期复核 → 按并发与暂停规则领取子任务 → SSH 执行 → 验证实际版本、依赖和健康状态 → 汇总父计划结果。

检测频率与秒级指标、30 秒巡检分开，避免在每秒循环中查询安装源。控制端停机时暂停新检查，恢复后每项策略合并补一次；补检查只产生结果与提醒。

已确认的预约到时可按计划执行，不在每台服务器上重复询问同一份未变化的计划。建议必须记录明确时区及允许启动的窗口；控制端停机或服务器离线错过窗口时标为“已错过，需重新安排”，不能恢复上线后立即补执行。恢复时仍在已确认窗口内的未开始任务，只有重新预检通过后才允许继续。窗口默认长度与检测间隔是待实施配置，不当作已确认数值。

执行前复核分组、类型、有效范围、地址、凭据、主机指纹、插件／配方修订、实际软件版本、精确包可用性与依赖。影响计划的变化使该项阻塞并暂停后续，要求重新预检和确认，不能改用另一个版本或跳过失败项继续。指标、普通巡检时间更新和语言切换不使计划失效。软件已经达到目标时记录“无需执行”及实际状态，不能仍运行重装脚本。

同一台服务器的升级、安装、移动和其他软件修改共用互斥规则，多个控制进程以数据库领取或租约避免重复执行。控制端异常退出不代表远端包操作停止；恢复时先核对远端任务标识、实际版本及包管理器状态，禁止立即重复派发。建议使用任务级远端互斥与结果记录辅助恢复，不需要远端常驻调度器。

建议将“关闭自动检测”与“取消已确认计划”分开：前者停止后续周期检测，后者控制已经安排的执行。关闭检测时同时展示未完成计划及其取消入口，避免用户误以为关闭检测就已取消升级。取消、暂停或插件卸载停止尚未开始的变更；已开始修改软件的工作须完成必要步骤及验证，不随意杀掉包管理器。插件释放注册与执行资源前等待或有序结束自己接受的工作。

检测的临时失败可以有限退避重试；软件变更的部分失败不能套用同一策略无限自动重跑。所有失败都记录实际版本、已发生的变化和需要人工处理的原因，不伪造远端回滚。

### 12.8 独立升级管理 Tab、依赖与持久状态

2026-10-20 用户调整导航要求：「服务器管理」改为侧栏中的可展开分组，下设「服务器实例」「服务器密钥」「升级管理」三个入口，覆盖此前将它们作为模块顶部页签的设计。进入「升级管理」后，在页面最顶部导航栏以「升级建议」「升级计划」「执行记录」三个 Tab 展示以下内容，顶部不再显示单一「升级管理」标题，内容卡片中不重复展示 Tab。平台设置及 Harness 保持现有导航。当前实施记录见 [版本、移动与升级管理](versions-moves-and-upgrades.md#d自动检测与升级管理)。

| 内容 | 职责与主要操作 |
| --- | --- |
| 升级建议 | 筛选分组、软件及版本，查看候选与阻塞原因，稍后提醒、拒绝本次或撤销，批量选择服务器并发起预检 |
| 升级计划 | 确认统一版本与时间，查看预检及依赖变化，立即执行或预约，取消、改期，重新预检后恢复暂停计划 |
| 执行记录 | 查看各机器进度与结果、失败原因、实际版本和远端变化，追溯对应计划与确认内容 |

服务器实例页保留升级状态、“需要升级”筛选及跳转入口，详情也可跳转到相关建议或计划。从实例页进入时可携带服务器、分组或软件筛选，面板明确展示这些条件并允许调整，支持进一步跨分组安排。两个页面共享同一份检测结果、建议处理和计划状态，不各自维护一份状态；返回实例页保留原有分组、搜索及分页。

登记和编辑的必要软件区域继续逐项展示软件名、类型范围、用户收紧条件、有效范围、实际版本、候选、检测开关和状态原因。逐软件检测开关仍在登记、编辑时设置，默认关闭；文案统一为“自动检测升级”，说明“只检测并提醒，升级需确认”。版本输入明确模式，避免固定版本与系列混淆。进入升级管理、切换视图或筛选、选择服务器，都不自动开启检测或触发升级；执行仍需确认具体计划。

建议分开保存三类状态，不把建议处理结果硬塞进已有任务的成功／失败枚举：

| 状态对象 | 至少记录的内容 |
| --- | --- |
| 检测策略与结果 | 每服务器每软件的开关、范围与规则修订、上次及下次检查时间、实际版本、候选与失败原因 |
| 建议处理 | 候选身份、推迟提醒截止时间、已拒绝目标及撤销、提醒去重信息；与已安排计划关联 |
| 升级计划及子任务 | 固定机器与精确目标、各机包和依赖计划、配置修订、确认记录、时区和窗口、并发及暂停策略、执行与验证结果 |

父计划建议区分草稿、待确认、已安排、执行中、已暂停、已完成、部分失败、已取消和已错过等状态，单台结果另外保留。暂停后仍有已开始任务时同时展示运行数量，不能用“已暂停”暗示机器上已经没有升级动作。确认记录不包含明文凭据。

检测开关不参与决定已确认计划能否修改某个依赖。比如 Compose 升级需要更新 Docker，即使 Docker 未开启检测，也可以在本次计划里明确列出并确认；但 Docker 的固定版本或有效范围不能被依赖操作绕过。无法形成兼容组合时阻塞计划。安装器不得在确认之外顺带更新关联包、整机执行无约束的包升级或重启整机。

升级 Docker 等服务可能影响业务，不能把“范围内”“小版本”或维护窗口承诺为无中断。配方需要声明服务重启、验证及已知影响，确认计划时展示；Docker 的 live restore 有版本及配置限制，也不能作为所有升级无中断的保证。[Docker live restore](https://docs.docker.com/engine/daemon/live-restore/)。

本功能管理声明的必要软件，不接管机器已有的包更新服务。外部更新导致漂移时重新判断、报告并复核计划，不自动改系统更新配置或静默降级。

### 12.9 建议实施顺序

1. 完成第 6 节的版本、配方和实际包解析，先验证只检测、不修改已安装软件的路径。
2. 持久化逐软件检测策略、建议及处理状态，实现推迟、拒绝、撤销和去重提醒。
3. 新增独立「升级管理」Tab，集中展示建议、计划与执行记录，接入明确的跨页选择及共同版本与依赖预检；实例列表加入升级状态、筛选和跳转入口，两处共享状态。
4. 接入一次计划的确认、立即执行或预约，绑定具体机器、版本、时间和修订；保留取消与改期入口。
5. 补齐批量父子任务、失败暂停、重启恢复与结果汇总，先用隔离测试验证中断和部分成功。

此顺序替代“开启自动升级后周期派发任务”的旧方案，不因已经具备安装脚本而省略建议、确认或批量预检。

### 12.10 补充验收项

- 不限定、完整固定版本、最小版本、完整上下界及大小版本系列均有边界测试；数字比较覆盖 `27.9` 与 `27.10`。
- `27`、`27.3`、`27.3.1` 含义不同，单点完整区间不绕过固定版本规则；系列上界、颠倒边界和空交集正确处理，用户条件不能突破插件范围。
- 初装与计划选择实际可安装的精确版本，不回退到范围外，不以网站最新号冒充包源版本。
- 逐软件检测默认关闭，登记和编辑正确保存；自动安装、周期检测、手动检测与确认升级的含义分别成立。
- 无论补丁、小版本还是大版本，检测到候选均不调用安装、升级或服务重启；只确认提醒时间也不能生成执行任务。
- 当前最新时继续检测，已达完整上限与固定版本正确显示原因，系列仍能检测未来补丁；源异常和权限不足不误报“没有更新”。
- 推迟到期只恢复提醒；拒绝同一服务器、软件、目标后多次检测不反复提醒，撤销有效，更高版本继续提醒；刷新、重启及切换语言不丢失处理状态。
- 侧栏「服务器管理」分组下提供「服务器实例」「服务器密钥」「升级管理」三个子入口；升级管理内的建议、计划和执行记录使用 Tab，完整响应平台中英切换。
- 实例页的升级相关内容保留为状态、筛选和跳转，现有分组侧栏、定高与分页保留；跳转条件明确、可调整，支持跨分组安排，返回保留原列表条件，两页结果与计划状态一致。
- 检测开关仍在登记、编辑中逐软件设置且默认关闭；进入面板、筛选与选择服务器均不自动开启检测或创建执行任务。
- “需要升级”筛选与已推迟、已拒绝、检测失败、已安排状态可区分；页内与跨页选择数量正确，确认后筛选变化不增添机器。
- 统一目标满足所有机器有效范围、系统架构、真实包源和依赖；无交集时明确阻塞或拆分，不隐式改成各自最新版，也不重装或降级已达目标的机器。
- 立即与预约均需确认具体清单、版本、依赖及时间；新版本发布不改变既定目标，跨大版本和服务影响明确展示。
- 任一子任务失败后，已排队及已领取但尚未开始的任务暂停，已开始任务有序结束；显示实际变化，显式恢复后重新预检，不重复成功项或伪造整体回滚。
- 控制端恢复只合并补检测；错过执行窗口不补升级；窗口内恢复须复核，控制端崩溃后不重复派发仍在远端运行的任务，同服务器软件修改串行。
- 排队后变更分组、类型、范围、实际软件、地址、凭据、主机指纹或插件定义，受影响计划阻塞并重新确认；指标、巡检时间与语言切换不误使确认失效。
- 关闭检测与取消预约分别生效且页面说明清楚；暂停、取消或卸载不随意中断已经开始的包操作。依赖变更须在确认计划中且不能绕过版本约束。
- 部分安装、版本验证或健康检查失败可区分；恢复、重试与改期需要显式操作，不因后台重试扩大变更范围。

类型和系统分组的实施进展见第 13 节。C、D 的实现与验证见 [版本、移动与升级管理实施记录](versions-moves-and-upgrades.md)。周期任务只检测升级；软件变更仅执行经过明确确认的计划。

## 13. 类型与系统分组阶段历史记录（2026-10-19，接口已替换）

本节 `registerGroup()` 已由 A2 替换，不能复制到当前插件。请使用 [当前注册示例](execution-foundation.md#当前插件接入方式)。

### 13.1 已实现范围

- 新登记默认 `builtin/vacant`，必要软件为空，自动安装关闭且不可勾选。`builtin/general` 的必要软件固定为 Docker Engine 与 Compose，按依赖顺序处理。必要软件不可由页面取消勾选，接口拒绝提交旧的 `install_component_ids` 字段。
- 登记和编辑页面根据目标分组显示类型、双语软件说明及自动安装开关。系统分组侧栏显示来源状态并隐藏删除按钮，DELETE 接口同样拒绝删除；普通分组继续支持创建、删除。分组排序按 `sort_order`、创建时间、UUID，不随翻译或名称变化。
- `server_groups` 保存 `kind/plugin_id/group_key/name_i18n/sort_order/definition`；系统身份唯一键为插件名加稳定分组键。重新注册更新同一行，保留 UUID 与服务器归属；普通名称唯一性与系统身份分别约束。
- `servers` 保存 `type_key/type_snapshot/config_revision` 与独立的容器巡检状态、最近成功时间。旧登记保持普通类型，新登记默认空置。SSH 成功即在线，缺 Docker 不再变成 SSH 故障；主机指标和终端继续独立使用 SSH。
- 必要软件检测分为已安装、缺失、未知。未知状态不触发安装；脚本返回成功仍须重新检测，安装后重连以刷新 SSH 用户权限。只执行当前类型的必要软件及依赖，不安装目录中的无关软件。
- Docker 容器巡检可选。Docker 不存在或巡检失败时显示明确状态和最近成功时间，保留上次容器观察，列表数量显示“—”，不会把失败当成零个容器。
- 软件定义修订包含依赖和脚本内容。脚本／定义变化使旧检测结果失效，排队安装任务校验配置修订和类型签名；配置变化后拒绝继续执行旧任务。同服务器任务串行，运行期间禁止修改分组、类型、连接及安装配置。

### 13.2 已实现的插件注册接口

A1 已为类型增加 `supportedOs`，软件配方增加同名的选择器数组；第 13 节原例保留为历史接口示意，不能直接用于 A1。A1 的完整最小例见下方第 14 节。完整 V2 的 `registerDefinitions()` 仍是设计稿。

宿主服务为 `ctx.serverManagement`，依赖声明为 `inject = ['serverManagement']`。`registerGroup(definition)` 返回 Cordis effect 的可等待释放句柄：`await` 等待注册完成，插件卸载自动释放；若需提前撤回，也可以调用该句柄。不要把注册结果放进模块级可变变量。

```js
import { fileURLToPath } from 'node:url'

export const inject = ['serverManagement']

export async function apply(ctx) {
  await ctx.serverManagement.registerGroup({
    plugin: '@example/compute',
    key: 'compute',
    name: { zh: '计算节点', en: 'Compute nodes' },
    order: 10,
    software: [{
      id: 'worker',
      name: { zh: '计算服务', en: 'Worker service' },
      summary: { zh: '执行计算任务', en: 'Runs compute jobs' },
      requires: [],
      detectScript: fileURLToPath(new URL('../scripts/detect.sh', import.meta.url)),
      installScript: fileURLToPath(new URL('../scripts/install.sh', import.meta.url)),
    }],
    types: [{ key: 'worker', name: { zh: '计算服务器', en: 'Compute server' }, software: ['worker'] }],
    defaultType: 'worker',
  })
}
```

示例中的脚本由贡献插件打包并提供绝对路径，注册时读取，页面不能提交脚本或路径。类型的持久键为 `@example/compute/worker`；显示名称不参与身份判断。软件 ID 在该分组的软件目录中唯一，不能覆盖内置 `docker`、`compose`；`requires` 引用同一目录的 ID，可引用内置软件。依赖自动展开，缺项和循环依赖导致注册失败。

省略 `types` 时使用两种内置类型、默认空置；显式提供时完全替换，自定义列表必须非空且 `defaultType` 指向有效项。插件、分组键与类型键稳定，名称必须有中文和英文；无效默认值、重复注册、冲突类型、未知配置字段会拒绝注册。目前没有版本范围字段，不能传入后被静默忽略。

自定义检测脚本退出码为 0，标准输出为单个 JSON 对象，例如：

```json
{"state":"installed","version":"1.2.3","detail":""}
```

`state` 只允许 `installed/missing/unknown`，`version/detail` 可选。只有明确返回 `missing` 才允许初装；非零退出、无效 JSON、权限或执行异常均为 `unknown`。检测脚本必须只读。安装脚本仅安装缺失软件、退出码非零即失败，不应隐式升级已安装软件；执行后平台重新检测并记录实际状态。

卸载开始后注册立即不可用于新任务，已取得定义的任务保留脚本快照，释放时等这些任务结束。数据库缓存保留分组、类型和名称，界面显示插件／类型不可用，不依赖缓存继续执行插件脚本。仍可查看、连接、采指标和编辑普通登记信息。

### 13.3 移组与类型转换的当前边界

列表的分组入口进入编辑表单，用户明确选择目标分组和类型。同一有效类型优先保留，否则预选目标默认类型。已有类型失效时保留原值并提示，不能自动改为默认值。

本阶段允许必要软件及配方修订相同的移组／改类型，以及转为空置（不卸载软件）。目标非空且必要软件或配方不同的转换，接口返回 `type_change_requires_preflight`，原分组、类型和远端软件保持不变；即使关闭自动安装也不能绕过。表单提示这一限制。

当前限制是阶段边界，不代表“空置改普通”这一需求已经完成。新增操作系统及允许破坏兼容性的前提后，已完成 [数据模型与插件契约设计基线](data-model.md)、A1 的配置／观察分离与操作系统登记，以及 [A2 中现有 Linux 初装所需的 V2 注册与计划执行基础](execution-foundation.md)。下一步仍需补齐版本范围的登记／编辑交互、冲突替换确认、移动预检及成功后提交移动。自动检测升级和独立「升级管理」Tab 排在版本／预检能力之后。第 13.2 节仅保留 A1 阶段的旧接口记录，不能用于当前插件。

## 14. A1 操作系统范围历史示例（接口已替换）

```ts
const supportedOs = [{
  family: 'builtin/ubuntu',
  versions: { kind: 'release' as const, version: '24.04' },
  architectures: ['x86_64', 'aarch64'],
}]

await ctx.serverManagement.registerGroup({
  plugin: '@example/compute', key: 'compute',
  name: { zh: '计算节点', en: 'Compute nodes' },
  software: [{
    id: 'agent', name: { zh: '节点代理', en: 'Node agent' }, supportedOs,
    detectScript: '/absolute/plugin/path/detect.sh',
    installScript: '/absolute/plugin/path/install.sh',
  }],
  types: [{
    key: 'worker', name: { zh: '工作节点', en: 'Worker' },
    supportedOs: { kind: 'explicit', selectors: supportedOs }, software: ['agent'],
  }],
  defaultType: 'worker',
})
```

类型无软件时可以声明 `supportedOs: { kind: 'all' }`。当前 `sh` 执行器拒绝将 Windows 声明为带软件类型的执行范围；其他自由文本也不能自动映射成 Ubuntu。自定义软件检测返回 `installed` 时必须同时返回非空 `version`，否则记录未知。软件持久身份为 `插件包名/软件键`，配方身份仍包括分组键；实际范围随配方内容参与修订。

这段接口仅记录 A1，A2 已切换注册及初装执行基础，不能继续调用。其他、系统版本、阶段边界与验证见 [A1 实施记录](database-redesign.md#7-a1-实施记录2026-10-19)。
