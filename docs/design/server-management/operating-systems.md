# 服务器登记的操作系统选择与类型、软件适用范围

实施状态（2026-10-19）：A1 已完成系统两行选择、保存、只读探测与类型／软件范围校验，详见 [实施记录](database-redesign.md#7-a1-实施记录2026-10-19)。自定义系统身份与 Windows 软件配方仍待 V2；目录不是安装能力承诺。

状态：需求分析，尚未实现。本文补充 [基础服务器管理](design.md) 和 [类型、系统分组、软件版本与升级](group-types-and-i18n.md)。截至 2026-10-19，登记表单、服务器记录和插件类型定义都没有操作系统字段，也没有按操作系统选择检测／安装配方。下文的接口形状是设计建议，不是现有接口。

数据实施前提已更新：当前没有服务器数据，不需要旧记录迁移；可以按 [数据库重构建议](database-redesign.md) 设计新结构，登记系统按必填处理。

## 1. 需求与边界

用户在登记服务器时选择操作系统。页面固定采用两行：第一行选系统大类，即 Windows Server、各常见 Linux 发行版或「其他」；第二行随大类切换，列出带版本号的具体系统，例如「Ubuntu 24.04 LTS」。选择「其他」时，第二行改为文本框，让用户自行填写系统名称和版本。编辑服务器时也应显示并允许更正原选择，否则登记错误无法修复。

服务器类型和必要软件均须声明适用的操作系统范围。先选分组及系统，再筛选该分组可用的类型；选定类型后，按该系统显示真正必要的软件、版本要求以及可用的检测和安装能力。页面筛选只是提示，保存、任务领取和执行前都由宿主重新校验。

「登记目录中有该操作系统」仅表示能识别或记录它，不表示当前插件已能在该系统上安装软件、采集指标或管理容器。现有软件检测与安装通过类 Unix 命令和 `sh` 执行，指标读取 Linux `/proc`；Windows Server 的这些能力需要单独实现并验证。SSH 是否能连接也取决于目标机的 SSH 服务，不能仅由选择项推断。

## 2. 两行选择器与初始目录

| 第一行：系统大类 | 第二行：预置版本选项（建议初始值） |
| --- | --- |
| Windows Server | Windows Server 2016、2019、2022、2025 |
| Ubuntu | Ubuntu 20.04 LTS、22.04 LTS、24.04 LTS、26.04 LTS |
| Debian | Debian 12、13 |
| Red Hat Enterprise Linux | RHEL 8、9、10 |
| Rocky Linux | Rocky Linux 8、9、10 |
| AlmaLinux OS | AlmaLinux OS 8、9、10 |
| 其他 | 文本框，填写完整系统名称与版本，例如 `openSUSE Leap 15.6` |

这是**预置选择目录**，不是承诺全部版本仍由发行方维护，也不是安装配方的支持清单。预置版本应作为可更新的数据维护；新版本发布时增加选项，不用修改已有服务器的系统身份。过去选过而后来从预置目录移除的版本，编辑页仍能展示和保存。RHEL、Rocky、AlmaLinux 的 `8`、`9`、`10` 是发行版的大版本系列；具体小版本可在远端探测中记录，配方若限定小版本，仍须按实际小版本预检，不能把「RHEL 9」误判为已确认兼容全部 `9.x`。

预置版本核对来源：[Windows Server 版本](https://learn.microsoft.com/en-us/windows/release-health/windows-server-release-info)、[Ubuntu 版本与生命周期](https://ubuntu.com/about)、[Debian 版本](https://www.debian.org/releases/)、[RHEL 版本](https://access.redhat.com/support/policy/updates/errata)、[Rocky Linux 发布信息](https://rockylinux.org/news)、[AlmaLinux 发布说明](https://wiki.almalinux.org/release-notes/)。实施时仍需复核目录及各配方的实测支持范围。

交互建议：第一行切换后清空旧的第二行选择，并要求重新选具体版本；不自动把不同发行版的相同数字视为同一个系统。新登记不预设 Ubuntu 或 Windows，也不允许空系统直接提交。语言切换只翻译「其他」、字段、提示等界面文案，已选系统和「其他」原文保持不变。

## 3. 系统身份与实际探测

预置项保存稳定的大类标识和版本值，例如 `family=ubuntu, version=24.04, edition=LTS`，显示名由目录生成；Windows Server 2025 保存 `family=windows-server, version=2025`。版本值是**操作系统版本**，与 Docker 等软件的版本范围分别建模。跨发行版不能只比较版本数字；Windows 的年份、Ubuntu 的年月和 RHEL 的主／小版本也不能直接套用软件的 SemVer 比较器。

「其他」保留用户填写的完整原文，并标记 `family=custom`。任意文字不应被猜成 Ubuntu、RHEL 或某个 Linux 兼容族，也不能拼进远端命令。后续插件若要支持自定义系统，建议先通过明确的系统标识／别名注册和只读探测，把该文本映射到一个可校验的身份；不能用模糊名称匹配来批准安装脚本。原始登记值和 SSH 探测到的实际发行版、版本、架构、探测时间分开保存，以便显示差异。

建议在建立 SSH 连接后做只读系统探测：Linux 读取发行版身份及版本；Windows 使用经验证的 Windows 远端执行方式。探测失败显示「未验证」，不能假装已匹配。探测结果不能静默改写用户选择，系统变化也不能让旧软件任务沿用原配方。用户可更正登记值，必要时重新预检软件、包源与依赖。登记与实际系统不一致时的保存及操作规则见第 7 节。

## 4. 类型、必要软件和配方的适用范围

建议将系统条件拆成三个位置，避免一个「支持 Windows」标记覆盖不同层次：

| 定义位置 | 作用 | 示例 |
| --- | --- | --- |
| 类型 `supportedOs` | 决定某系统下是否能选该类型 | 空置类型支持所有可登记系统；只为 Ubuntu 验证过的计算类型仅支持 Ubuntu 22.04～26.04 |
| 类型中的必要软件项 `whenOs` | 决定该软件在这个类型及系统上是否必要 | 同一类型在 Ubuntu 上需要某个 Linux 代理，在 Windows Server 上需要对应 Windows 代理 |
| 软件检测／安装配方 `supportedOs` | 决定能否在该系统与架构运行具体脚本、解析包版本 | Ubuntu 上运行 `sh` 配方；Windows Server 必须使用经验证的 Windows 配方 |

操作系统范围建议支持「一个或多个发行版／系统大类」及各自的版本系列或上下界，边界在**同一个大类内**解释。例如 `ubuntu: [22.04, 26.04]`、`windows-server: [2022, 2025]`；跨发行版用明确的多个条目表达，不设隐式「所有 Linux 均兼容」。范围语法、版本比较器和包含端点须随系统大类确定，注册时拒绝反向区间、未知大类和空交集。类型适用范围与每项软件的 `whenOs`、配方的实际支持范围须有可执行的交集；不能因某项配方不支持选定系统就悄悄删掉仍然必要的软件。

插件系统分组可声明类型范围、按系统生效的软件要求及配方能力；未提供自定义类型时仍继承内置类型，但内置类型也必须经过系统筛选。新的 [V2 契约](data-model.md#4-插件注册与执行协议) 将替换现有 `registerGroup()`，类型／配方修订参与已有任务签名、缓存和插件卸载保护。插件不可通过页面提交任意脚本路径。若同一软件在不同系统上需要不同配方，软件稳定标识保持一致，按系统和架构选择配方；版本要求仍受类型和用户进一步收紧的规则约束。

已确认 `builtin/vacant` 适用于所有可登记的系统，必要软件为空；它不触发 Docker、Compose 脚本。现有 `builtin/general` 固定要求 Docker Engine 与 Compose，暂时只对**经安装配方验证的 Linux 系统及版本**开放。Windows Server 在内置类型中只能选空置；专门的 Windows 配方、探测与验证完成前，不能选择内置普通类型。插件若明确提供并验证了适用于 Windows 的自定义类型和配方，可按其自身声明开放。「其他」系统的类型与配方规则见第 7 节。

## 5. 登记、编辑、移动与升级的联动

1. 登记页先选系统，再根据系统与分组给出可选类型和默认类型。若分组默认类型不适用，建议优先选该分组明确声明的、适用系统的备用默认类型；无适用类型则说明原因并阻止提交。必要软件区域只展示当前系统上实际生效的项，并标明「配方不可用」「尚未检测」等事实，不把不可执行当成已安装。
2. 切换系统时重新计算类型及软件。原类型不再适用时要求重新选类型，不能静默保存旧类型；已填写的地址、凭据等表单内容保留。切换语言不重置系统、类型或用户输入。
3. 编辑既有服务器的系统选择属于关键配置变更：服务端重验分组、类型、必要软件、配方和自动检测升级策略。若导致软件安装／替换需求，沿用现有文档约定的只读预检、明确确认、远端成功后提交绑定；不能通过普通 `PATCH` 绕过。旧任务、升级建议和已确认计划需要按新系统身份与实际探测结果重新校验或阻塞。
4. 移组或改类型时同时检查目标类型的系统适用范围，以及目标必要软件和配方。目标类型列表只提供该服务器系统可用的选项；不能保留已不适用的原类型。软件变更、失败后保留原绑定、报告远端实际变化的规则与 [原设计](group-types-and-i18n.md#72-移动服务器) 一致。
5. 自动检测升级与批量统一版本计划也必须把系统、具体版本、架构及真实包源加入候选和执行前复核。相同软件的统一目标版本可对应不同系统包，但每台都必须有经验证的配方及精确包版本；没有共同可执行目标时阻止批量计划或要求拆分。变更系统登记或探测到系统已变时，旧计划不能继续执行。

## 6. 数据与实施建议

- 服务器登记配置保存用户声明的系统身份和「其他」原文；另存最近一次实际系统／架构探测及时间、状态。接口返回结构化字段，不以显示字符串作为系统判定依据。新登记系统必填，探测未完成时保留「未验证」；当前没有服务器数据，无需为旧记录回填或猜测系统。
- 预置目录有稳定 ID、版本、可选的中英显示名和目录修订；新增发行版／版本不改旧服务器的 ID。插件的系统范围可引用明确 ID；插件若提供新系统身份，应定义其标识、显示名和探测／匹配规则，并遵守注册生命周期。
- 软件配方要声明支持的系统、版本和架构，以及远端解释器和安装能力。注册时校验声明格式；执行前用实际探测、目标版本与包源再校验。Windows 需要专用探测、脚本执行与指标／容器适配，不复用现有 `sh` 或 `/proc` 命令。
- 先实现目录、两行选择、持久化及后端类型过滤；再实现只读系统探测与不匹配提示；随后扩展配方选择、安装／移动预检，最后把系统条件接入升级建议和批量计划。每阶段都要保留「空置、无软件变更」路径。

## 7. 已确认的产品规则

用户于 2026-10-19 确认：

1. Windows Server 在现有内置类型中只能选择空置服务器；内置普通服务器暂限已支持的 Linux 系统。插件日后提供经验证的 Windows 专用类型与配方时，可按插件声明使用。
2. 登记值与 SSH 探测到的实际系统不一致时，允许保存服务器记录，但阻止安装、移组、改类型和升级，明确提示修正登记系统并重新预检。修正登记系统本身不应被此规则拦住。
3. 「其他」自由填写的系统，只有在插件**明确声明支持**该系统时才可使用对应类型和软件配方；没有明确支持时仍可选择空置服务器。不能凭名称相似或 Linux 血缘自动套用配方。

## 8. 验收要点

- 两行选择按大类切换，Windows Server 与常见 Linux 发行版显示带版本号的选项；选「其他」后第二行变为文本框，原文可回显，系统必填。
- 切换分组、系统、类型、语言时，类型和必要软件实时更新，地址、凭据等未提交输入不丢失；接口直接提交不适用类型或配方也会拒绝。
- 同一类型在不同系统的必要软件条件按声明生效，依赖不被漏掉；未声明支持的系统不执行脚本，不把检测失败当成「未安装」。
- 空置类型不安装任何必要软件；Windows 列在目录中不导致现有 Linux `sh` 脚本或 `/proc` 指标命令在 Windows 上运行。
- 编辑系统、移组、改类型、安装与升级执行前重新核对实际系统和配方；关键变化阻止旧任务沿用原计划，失败时不虚报远端回滚。
- 「其他」文本及将来从目录移除的已选版本能正确回显；新登记不能遗漏系统，未探测不冒充已匹配；浏览器输入不能伪造插件支持范围或提交脚本路径。
