# 「服务器实例」列表精简与状态展示

## 1. 当前问题

当前列表有 13 列：名称、地址、服务器类型、区域、可达状态、必要软件、CPU、内存、硬盘、Docker、容器数、最近检查、分组。Docker 版本和容器数不适用于所有服务器；分组已由左侧分组栏选择，列表再占一列没有必要。CPU、内存、硬盘各占一列也让表格过宽。

当前「必要软件」列是**安装结果汇总**，显示「已满足／待安装／未确认／定义不可用」。空置类型没有必要软件时也显示「已满足」，容易让人误以为完成过软件安装。用户要看的「是否安装必要软件」是登记／编辑时的**安装选择**，两者不能混用。当前「可达状态」只表示连接结果，不能表达「升级中」等整台服务器的当前状态。

## 2. 改版后的主列表

建议保留以下 8 列，顺序如下：

| 列 | 展示内容 |
| --- | --- |
| 名称 | 登记名称；点击进入服务器详情 |
| 地址 | 主机地址与 SSH 端口 |
| 操作系统 | 登记的系统及版本，如 `Ubuntu 24.04 LTS`；新登记必填，实际探测情况另行记录 |
| 类型 | 当前分组下选择的服务器类型；现有「服务器类型」列继续使用 |
| 状态 | 一条面向用户的总体状态，见第 4 节 |
| 是否安装必要软件 | 登记／编辑时保存的自动安装选择，见第 3 节 |
| 资源概览 | 在一个单元格内紧凑展示 CPU、内存和硬盘用量；尚无数据时用「—」，不要误报为 0 |
| 最近检查 | 最近一次有效检查时间；与状态一起判断信息新旧 |

「操作系统」是新增能力，目前尚无字段或探测结果；「类型」在当前列表中已经存在。登记和编辑表单仍按 [操作系统设计](operating-systems.md) 的两行方式选择系统。主列表显示登记值；与远端实际系统不一致时，由「状态」提示异常，详情展示两者的具体差异。

从主列表移除「区域」「Docker」「容器数」「分组」和独立的 CPU／内存／硬盘列。区域放在详情，仍可作为搜索或筛选条件；Docker 与容器信息只在相关服务器的详情中展示，不要求空置服务器拥有 Docker。左侧分组栏继续负责选择分组；选「全部服务器」时也不额外增加分组列，需要看归属时进入详情。列表现有的定高、表头、搜索、分页以及分组切换行为保留。

## 3. 「是否安装必要软件」的确切含义

这一列回答的是：**用户是否在登记／编辑时选择了让系统自动安装当前类型所要求的、尚未安装的必要软件？** 数据来源是服务器保存的安装选择，目前字段名为 `auto_install`，重构时可重新命名；它不取自探测出的软件状态。

| 情况 | 列表显示 | 含义 |
| --- | --- | --- |
| 当前类型有必要软件，安装选择开启 | 是 | 允许按既有规则补齐缺失软件；不表示任务已经完成 |
| 当前类型有必要软件，安装选择关闭 | 否 | 不自动补齐；不表示软件一定没有安装 |
| 当前类型没有必要软件，如空置服务器 | 不适用 | 没有可安装的必要项；表单中的安装选择禁用 |
| 类型／配方定义不可用 | 保留已保存的「是／否」并提示「当前不可执行」 | 只反映原选择，不能承诺可继续安装 |

已装、缺失、未知、版本不符等**实际软件结果**放在详情里的必要软件区域逐项展示；需要处理时也通过总体「状态」提醒。安装选择不改变类型定义的必要软件集合，不授权替换已安装版本，更不等于「自动升级」或「自动检测升级」。仅在真正执行安装时才显示「安装中」；开关为「是」、任务排队或任务失败都不能显示为已经安装成功。

## 4. 统一「状态」列

列表只显示一个主要状态，同时允许通过详情查看连接、软件、任务的原始状态与原因。它是由已有及后续的连接结果、类型要求和任务进度计算出的展示值，不能只把「可达状态」文字替换成「状态」。建议规则：

| 主要状态 | 触发条件或展示原则 |
| --- | --- |
| 待验证 | 尚未完成有效连接／系统检查，不能判断是否正常 |
| 正常 | 最近检查有效，服务器可连接，当前没有已知的类型或必要软件阻塞；空置类型不因缺 Docker 而异常 |
| 断开 | 无正在执行的软件变更，最近一次连接检查明确失败 |
| 安装中 | 必要软件安装任务已经开始执行；排队不算安装中 |
| 升级中 | 已确认的升级任务已经开始执行；仅检测出新版本或预约了升级不算升级中 |
| 需处理 | 服务器可连接，但必要软件缺失／状态未知、类型定义不可用、系统与登记不符，或最近一次软件变更失败等需要人工处理 |

同一时刻可能有多个事实。例如升级中的服务重启可暂时导致 SSH 断开，主列表仍显示「升级中」，详情展示连接变化和任务进度；任务结束后再按最新事实重算。未执行的预约升级可以在详情和升级管理中显示计划，不能冒充「升级中」。失败或超时的任务不能永远占用「安装中／升级中」。巡检或指标采集的短暂失败也不能直接覆盖已确认的连接结果；状态依据与刷新时效由实施时统一定义。

总体状态不代替后端的独立事实。连接结果、必要软件符合情况、系统匹配情况、任务状态和最近检查时间仍分别存储，供详情、诊断、移动预检和升级计划使用。宿主返回稳定状态码和原因，前端按平台语言翻译；不通过解析任务输出中的中文句子来判断状态。

## 5. 与现有流程的关系

- 操作系统及版本取自新的登记字段。Windows Server 暂不能选择内置普通类型，只有经验证支持该系统的插件类型／配方才可执行软件操作；列表有 Windows 项不代表具备 Docker 或容器能力。
- 登记值与 SSH 实际探测的系统不一致时，按已确认规则允许保存，但阻止安装、移组、改类型和升级；总体状态显示「需处理」，详情说明差异和修正入口。
- 普通服务器要求 Docker 与 Compose，或系统分组类型要求其他软件时，「是否安装必要软件」只显示这台服务器保存的安装选择。若软件已经安装，即使选择「否」，也可以处于「正常」。若选择「是」但安装失败，则显示「需处理」，而不是因为开关开启就显示「正常」。
- 升级管理仍是服务器管理内独立 Tab。列表「升级中」只反映实际执行状态；候选、推迟、拒绝、计划和具体版本在升级管理中处理。主列表可保留「需要升级」筛选和跳转入口，不增加每个软件的版本列。
- 搜索至少继续覆盖名称和地址，增加操作系统及类型；区域即使不在表格中也可继续作为搜索条件。切换平台语言不重置分组、搜索词、页码或详情入口。

## 6. 验收要点

1. 主列表按第 2 节显示 8 列；分组侧栏、定高和分页仍可用。空置服务器不出现 Docker／容器列占位。
2. 「是否安装必要软件」对有必要软件的类型显示「是／否」，空置类型显示「不适用」；与真实安装结果不相互推断，详情可查看逐项结果。
3. 已连接的空置服务器即使没有 Docker 也可显示「正常」；连接失败显示「断开」；真实执行升级时显示「升级中」，仅预约或仅检测到新版本时不显示「升级中」。
4. 安装失败、系统不符、定义不可用等情形显示「需处理」及可查看的原因；任务完成或失败后状态及时退出「安装中／升级中」。
5. 操作系统和类型随平台语言正确显示；手填系统原文保留；未知指标用「—」，尚未完成系统探测时不猜测实际版本。

本文描述目标界面和展示语义。当前代码仍使用原 13 列、独立的可达状态及必要软件结果列；操作系统字段和升级任务也尚未实现。
