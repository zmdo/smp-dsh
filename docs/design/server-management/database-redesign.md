# 服务器管理数据库结构问题与重构建议

状态：2026-10-19 已完成结构评估；随后完成 [数据模型与插件契约详细设计](data-model.md)，附独立 DDL 与 TypeScript 契约稿。尚未修改运行时迁移、应用数据库或业务代码。本文保留问题依据和改造进度，字段及执行规则以详细设计为准。

相关需求：[类型、插件系统分组与升级](group-types-and-i18n.md)、[操作系统选择与兼容范围](operating-systems.md)、[服务器实例列表](server-instances-list.md)。

## 1. 用户已确认的前提

- 当前没有服务器数据，不需要搬迁或兼容旧服务器记录。
- 当前没有发布、部署，可以对数据库结构、插件注册接口和服务器管理接口进行破坏兼容性的更新。
- 不再为旧的 Docker 默认语义、旧字段或旧接口保留兼容层。初始化后的新登记仍默认空置类型。
- 数据库建表、初始化及版本管理仍要保留。本模块重构范围是服务器管理相关对象；这不是重置整个平台数据库或清理其他模块数据的要求。

以上前提替代此前“沿用旧服务器为普通类型、只能追加迁移、必须保留旧字段”的设计约束。既往实施记录中提到的回填与测试保留为历史事实，不再作为新模型的验收要求。

## 2. 当前结构的主要问题

评估依据是当前 [基础建表](../../../plugins/database/migrations/0010_server_management.sql)、[类型扩展](../../../plugins/database/migrations/0012_server_types.sql) 及服务器管理插件读写代码。现有结构适用于早期登记、SSH 检查和 Docker 巡检，不能完整支撑已确认的操作系统、逐软件策略与批量升级要求。

| 编号 | 当前事实 | 问题及后果 |
| --- | --- | --- |
| DB-01 | `servers` 混合登记配置、连接结果、资源采样、软件和容器状态 | 配置修改和后台观察共用主记录，生命周期及更新时间含义混杂。需要明确配置修订与观察时间，避免普通采样使用户确认失效。 |
| DB-02 | 主表含 `docker_version/compose_version`；连接状态枚举仍允许旧的 `docker_unavailable` | 对 Docker 存在特殊依赖，插件每增加一种软件不应再增加主表专用列；连接结果也不应取决于有没有 Docker。 |
| DB-03 | `install_component_ids` 是文本 JSON，保存可由类型推导的必要项；`component_status` 把各软件检测结果放进整段文本 JSON | 必要项和类型重复保存，逐软件筛选、更新、版本策略及定时检测缺少合适的数据粒度。当前检测会重写当前类型的软件集合，不能把它当成完整、持续保留的软件观察记录。 |
| DB-04 | 没有操作系统字段 | 无法分别表达用户登记的系统、远端实际系统、版本及架构，也无法保存系统不匹配的检查依据。 |
| DB-05 | 没有逐软件检测策略、升级建议及处理记录 | 版本范围收紧、自动检测、推迟提醒、拒绝指定目标和撤销不能持久化；不能只放在浏览器或通用任务输出中。 |
| DB-06 | `ops_jobs` 只有动作、简单任务状态、输出摘录及配置／类型修订 | 缺少确认计划、固定机器清单、精确包与依赖、预约窗口和父子执行结果，无法兑现统一版本、批量暂停、移动成功后提交等要求。 |
| DB-07 | 任务没有细分执行阶段和远端操作标识；启动恢复将 `running` 直接标成失败 | 无法准确区分连接、预检、安装、验证，也不能判断控制端退出后远端是否仍在安装。未来软件变更不能根据这个失败标记直接重复执行。 |
| DB-08 | 列表每秒全量读取服务器，按分组加载定义；容器计数另由子查询取得，前端筛选分页 | 新增软件与任务聚合后，应统一设计列表查询和筛选语义，避免逐服务器追加查询或连接多张一对多表造成重复行及错误计数。 |

第 DB-01 项不是指现有实现完全没有隔离措施：已有 `config_revision` 避免把一般巡检的 `updated_at` 当成配置变化。这个概念应保留，并在新结构中明确哪些操作会增加修订。

## 3. 建议的数据职责

下面是目标逻辑模型，不代表全部表已经批准、建立或必须一次性实现。

| 对象／建议表 | 职责与处理建议 |
| --- | --- |
| `server_groups` | 保留用户／系统来源、插件身份、稳定分组键、国际化名称、排序及必要的定义快照；系统身份与用户名称分别约束。 |
| `ssh_keys` | 保留加密凭据、指纹及服务器引用。认证方式与凭据引用须一致，避免同一服务器出现两个含义不清的凭据来源。 |
| `servers` | 保存登记配置：名称、地址、端口、认证、分组、类型、声明的系统与版本、「其他」原文、是否安装必要软件及配置修订。 |
| `server_runtime` | 每服务器一行最新观察：连接结果、实际系统与架构、主机资源和各自检查时间。暂不因本次需求额外引入资源历史时序库。 |
| `server_software_observations` | 每服务器每软件的实际观察：检测状态、实际软件版本、原始包版本、来源、检测时间和配方修订。保留上次有效结果与本次检测失败的区别；移组后不因软件不再必要就谎称已卸载。 |
| `server_software_policies` | 每服务器每软件的用户收紧范围、自动检测开关、检查调度和推迟提醒时间等策略。有效要求仍受插件类型和操作系统约束。 |
| 升级建议记录 | 保存服务器、软件、目标版本身份、候选有效性、拒绝及撤销。按稳定身份去重，重复检测不能消除用户的拒绝选择。 |
| 变更计划及目标服务器明细 | 保存固定服务器清单、源与目标分组／类型、配置修订、精确包和依赖变化、确认内容、执行窗口与并发／暂停策略。安装、替换、移动、升级共享必要的预检与执行基础。 |
| 执行任务及步骤记录 | 重构现有 `ops_jobs`，关联计划并记录尝试、实际执行阶段、结果、领取／心跳信息及远端操作标识。一次计划可以有重新预检后的重试，不能覆盖掉之前的实际结果。 |
| `server_containers` | 保留为可选能力的观察记录，供相关服务器详情使用；不再要求主列表为所有服务器读取容器数量。 |

需要持续查询、独立调度和更新的对象用独立行及明确关联表达。国际化文案、版本约束和已确认的不可变计划可使用经过结构校验的 JSONB，不要求把每个嵌套属性都拆成一张表。精确版本、包源及依赖应有快照，执行时不得重新解释成“安装当时最新版”。

类型与软件要求由插件注册提供。数据库的类型、分组定义快照用于展示、审计和解释既有计划；可执行性必须核对当前插件注册及配方修订。插件卸载后，缓存不能继续授权执行脚本。

软件稳定身份与配方身份分开：同一个真实软件跨分组仍可比较，不能因为换插件而失去版本冲突判断；不同真实软件也不能仅因名称相同就合并。需要明确身份规则，再建立每服务器每软件的唯一约束。操作系统及架构决定适用配方，用户填写的系统名称不直接构成安装能力声明。

## 4. 列表聚合与统一状态

新列表每台服务器仍只有一行，建议由宿主统一组合：登记配置、最新运行观察、当前类型定义、必要软件符合情况，以及正在执行的有效任务。分组字段继续用于筛选，但不占列表列；软件与任务应先按服务器汇总，避免直接多表连接产生重复行。后端筛选、排序、分页及计数应采用同一套判定规则，不能只对当前页计算状态后再筛选整个集合。

「是否安装必要软件」来自登记中保存的安装选择，当前字段名是 `auto_install`，重构时可重新命名。它不能从“实际软件已安装”推导，也不能作为“安装成功”的证据；空置类型显示「不适用」。

「状态」是计算后的展示值。连接、系统匹配、必要软件实际结果和任务阶段分别存储，由服务端返回稳定的状态码及原因，再按语言翻译为正常、断开、安装中、升级中、需处理等。不要由不同后台任务争相覆写一个缺乏原因的状态字符串。需要处理的失败应关联当前仍未解决的问题，不能因为历史上曾有失败就永久异常。

`test_connection` 可能包含自动安装步骤，单靠动作名和 `running` 无法准确表示“安装中”；执行阶段必须结构化记录。升级中暂时断连、任务结束、控制端重启恢复等情况也要依据任务与最新观察共同判断。连接检查时间、系统检查时间和资源采样时间应分别保留。

## 5. 重构要求与验证重点

- 取消旧服务器回填、旧字段双写和旧接口别名。保留新登记默认空置、软件检测未知不能视为缺失、已确认计划才能替换／升级等业务规则。
- 重新整理服务器模块的建表与初始化过程。现有迁移执行器按文件名跳过已执行文件，因此仅编辑旧 SQL 不会更新开发数据库；实施时必须明确相关空表及模块迁移记录的重建方式，不能只改文件后假定数据库已生效。
- 保留配置修订与配方修订，绑定预检及执行计划。指标更新不使确认失效；地址、凭据、系统、分组、类型及安装策略的关键变化要重新校验计划。
- 增加有业务依据的唯一约束、外键、状态与字段约束，以及分组筛选、软件定位、待执行任务、到期检测所需索引。保证同服务器软件变更互斥、同任务幂等、执行者失联后不会重复修改远端。
- 软件操作中断后的恢复需要核对远端实际情况，不能把数据库事务回滚或任务失败等同于远端软件没有变化。移动成功后提交目标绑定，失败保留原绑定并报告实际变化。
- 验证全新初始化、插件注册／卸载、未知检测、类型与系统约束、任务并发及中断恢复；升级和移动的确认边界在对应功能实现时补齐。不会为了不存在的旧服务器记录保留兼容测试。

新的数据模型与插件契约已形成设计基线。下一步进入基础重构与操作系统登记的实际编码，按 [详细设计的阶段与验收](data-model.md#9-实施顺序与验收) 推进：

1. 重构登记、运行观察、逐软件数据与现有任务基础，接入操作系统登记及只读核对，恢复并验证现有已实现能力。
2. 实现类型／软件的系统范围筛选和列表精简；统一状态按实际已经具备的执行阶段计算，不提前显示尚不存在的升级能力。
3. 实现版本范围、精确包解析、预检与一次性确认，完成涉及安装／替换的移组及类型转换。
4. 实现逐软件检测策略、升级建议与处理，接入独立升级管理 Tab、批量版本计划、预约调度及失败恢复。
5. 按新模型补齐会话工具及权限规则。

该顺序替代此前直接从版本范围开始推进的建议：新增操作系统和允许破坏兼容性这两个前提，使数据库与插件契约应先完成调整。重构现有基础与实现未来升级能力按阶段验收，不因记录了表名或需求就视为功能已完成。
