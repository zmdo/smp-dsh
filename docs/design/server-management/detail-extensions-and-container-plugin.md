# 服务器详情侧栏、配置扩展与容器服务器插件

日期：2026-10-20。状态：设计提案，尚未实施。代码核对基线：`ces/develop`，`7b902a0`。

本次只新增设计文档。页面、插件、数据库、服务器和运行配置均不在本次修改范围内。本文件作为后续实施依据；涉及“普通服务器内置”“所有 Linux 服务器可选容器巡检”的旧文档，以本文件的新设计为目标，旧实施记录继续保留其历史含义。

## 1. 用户要求与设计决定

用户明确要求：

1. 点击服务器实例后，进入带局部侧边栏的详情工作区，包含“服务器详情”“任务报告”“终端”“配置”。
2. 基础详情移除容器列表；任务报告从基础详情独立为面板。
3. 其他插件可以增加详情侧栏入口和对应面板，也可以增加服务器配置栏目。
4. “普通服务器”更名为“容器服务器”，并由独立插件提供，不再是服务器管理的内置类型。
5. 用户补充确认：原容器列表由新插件提供独立“容器”面板，仅在适用服务器上显示，用它验证面板和配置扩展。
6. 用户确认容器类型进入公共可选目录：普通用户分组、未分组和未限定类型的系统分组都可选择，登记默认仍为空置服务器。
7. 用户确认同一服务器内切换详情、任务报告、终端、配置及插件面板时保留终端连接；退出详情工作区、切换服务器或主动断开时关闭。
8. 用户确认“自动采集容器清单”默认开启，可在容器设置中关闭；关闭只停止周期清单采集，手动刷新和必要软件健康检测继续保留。

设计采用以下行为与命名：

| 项目 | 方案 |
| --- | --- |
| 核心内置类型 | 只保留“空置服务器 / Vacant server”，仍为默认选择 |
| 新插件名称 | 包名 `@smp/console-server-containers`，目录 `plugins/server-containers` |
| 插件类型名称 | “容器服务器 / Container server” |
| 类型的可选范围 | 插件显式加入公共类型目录；普通用户分组、未分组和继承公共目录的系统分组可选择 |
| 专属系统分组 | 容器插件本身无需创建，类型和分组解耦 |
| 容器入口 | 选中容器类型、插件可用时显示；暂未安装 Docker 也显示安装状态和下一步入口 |
| 配置扩展示例 | “容器设置”栏目，提供“自动采集容器清单”开关，默认开启，周期沿用核心巡检周期 |
| 终端连接 | 首次进入终端时连接；同一服务器内切换面板保持，退出详情工作区、切换服务器或主动断开时关闭 |
| 插件加载 | CES 配置显式加载正式容器插件，不能由服务器管理内部偷偷加载，也不依赖临时示例插件 |

其中，独立“容器”面板、类型开放范围与登记默认值、终端切换行为、容器清单采集开关行为均已由用户确认。包名、目录和具体接口形态仍是实施方案，不影响已确认的产品行为。

## 2. 当前实现与需要调整的边界

本节来自当前源码，不以早期设计文档推断实现状态。

| 当前实现 | 对本需求的影响 |
| --- | --- |
| `ServerDetail` 同时渲染基础信息、必要软件、容器表格和 `TaskHistory` | 需要拆成工作区外壳与独立面板，而非继续在详情组件内堆条件 |
| `ServersPage` 在 `list/form/detail/terminal` 四种屏幕间切换 | 终端和编辑当前会离开详情，需要纳入同一服务器工作区 |
| `useServerDetail` 每秒获取包含容器字段的详情 DTO | 基础数据和扩展数据应分开获取，未打开的面板不应持续加载大列表 |
| `TaskHistory` 已有服务端分页、查询及五秒刷新 | 复用查询和展示能力；本次主要改归属、挂载时机和视图状态保存 |
| `registerDefinitions()` 已支持插件软件、配方、类型和系统分组 | 可继续作为容器类型的接入基础，但尚无详情面板、服务器配置和巡检扩展契约 |
| `defaultOptions()`、系统组默认类型与删除分组校验硬编码空置／普通两类 | 只把普通类型移进插件，会导致用户分组不可选或删除分组时错误拒绝，必须一起去除硬编码 |
| `builtinCatalog()` 和 `builtinTypes()` 内置 Docker、Compose、普通类型 | 类型、软件和专属配方都要移交容器插件，核心只保留通用解析和执行能力 |
| `inspectJob()` 对已验证的非 Windows 系统调用 `inspectContainers()` | 当前并非仅因勾选“安装必要软件”才读取容器；插件化后必须由类型、插件和采集设置决定 |
| 核心观察 repository 同时写软件事实、容器清单和容器扫描状态 | 需分离通用观察与插件业务存储，并避免容器读取覆盖必要软件验证结果 |
| `ServerDto` 含 `docker_version/compose_version/containers*` | 基础 DTO 应去除容器专属字段，必要软件版本继续由通用软件观察提供 |

## 3. 页面布局与信息归属

“详情侧栏”是服务器实例页面内部的导航，当前全局侧栏仍承担“服务器实例 / 服务器密钥 / 升级管理”的导航职责。进入详情后，顶部全局导航仍选中“服务器实例”。

```text
顶部导航：服务器实例

返回服务器实例   服务器名称 · 地址:端口 · 状态
┌──────────────────┬───────────────────────────────────────┐
│ 服务器详情       │ 当前面板标题                          │
│ 任务报告         │                                       │
│ 终端             │ 当前面板内容                          │
│ 容器（插件）     │                                       │
│                  │                                       │
│ 配置             │                                       │
└──────────────────┴───────────────────────────────────────┘
```

基础入口相对顺序固定为“服务器详情 → 任务报告 → 终端 → 配置”。插件面板放在终端与配置之间，按 `order`、稳定键排序；配置位于末尾。扩展入口不会替换或覆盖基础入口。

局部侧栏建议宽度 180～220px，右侧占剩余空间。整体使用现有面板、颜色、边框和间距变量；在可用视口高度内布局，长内容在面板内滚动。任务和容器表格有独立滚动区与分页，不把整个页面无限撑高。窄屏折叠为面板选择控件，名称仍完整可读。

工作区外壳显示一次服务器名称、状态、地址和返回入口；右侧标题随所选面板变化，不再重复套一层以服务器名称为标题的大面板。返回实例列表时保留原分组、查询、排序和页码。

### 3.1 服务器详情

展示通用信息：

- 登记名称、地址、SSH 用户、区域、所属分组、服务器类型。
- 声明系统、探测系统、架构、系统核验结果、主机指纹。
- 统一状态及原因、最近检查时间、资源指标和采集时间。
- 必要软件表格：软件名称、版本要求、安装／检测状态、已安装版本；版本来自通用软件观察。

保留“测试连接”“刷新信息”“补齐必要软件”“查看升级”等相关操作。操作进入后台任务后，提示已排队，并提供“查看任务报告”的定位入口。分组／类型调整和登记信息编辑统一从配置进入。

基础详情移除独立 Docker、Compose 字段和容器列表。Docker、Compose 是容器类型的必要软件时，仍会自然出现在通用必要软件表格中。

### 3.2 任务报告

独立标题为“任务报告”，复用当前任务查询接口和结果格式：查询词、任务类型、状态、时间范围、分页、每页条数。结果和失败原因继续用可读文本／列表，不能要求用户读取 JSON。

沿用现有规则：周期巡检成功不逐次进入列表，每小时汇总成功情况；失败保留独立报告。手动操作、安装、移动和升级按既有规则记录。插件巡检也遵循同一规则，不能另建一个每轮都刷屏的任务源。

筛选和页码按服务器保存于本次页面实例状态；切换到详情再返回不会丢失。切换服务器时使用该服务器自己的状态，不能显示上一台机器的结果。默认查询最近记录。

从详情操作进入任务面板时，可按任务 ID 高亮／定位本次任务；普通切换仍保持用户筛选。全局“升级管理 / 执行记录”继续提供跨服务器的升级视角。

### 3.3 终端

将现有终端放进工作区，标题为“终端”。用户已确认连接归属于当前服务器详情工作区：首次进入终端面板时才建立 WebSocket／SSH；在同一服务器内切换到详情、任务报告、配置或插件面板时保持连接，返回终端继续使用同一会话。

退出整个详情工作区（包括返回实例列表、进入其他全局页面）、切换服务器、主动断开、关闭／刷新浏览器页面或卸载服务器管理时关闭连接。容器等扩展插件卸载不关闭核心终端连接。地址、端口、SSH 用户、认证或主机指纹等连接身份发生变化后，关闭旧连接并提示按新配置重新连接，防止页面已显示新地址而终端仍操作旧主机。

终端会话由 `ServerWorkspace` 下的专用会话控制器持有，终端视图挂载与否不决定连接存活。控制器保留有界输出缓冲，隐藏期间继续接收输出；切回时恢复显示和尺寸。切换面板不重复连接、不重放输入，隐藏终端不接收键盘事件。用户主动断开或网络连接失败后，展示重新连接按钮，不因普通重渲染或切回面板自动重连。

连接、错误、断开和重新连接状态在面板内展示。DOM 尺寸测量和键盘事件绑定使用本组件 ref，避免当前全局 `.terminal-host` 查询在多面板场景下指向错误节点。

工作区退出时同时清理连接中和已连接会话；迟到的 SSH 连接必须关闭，不能在退出后变成无人持有的后台会话。正常输入输出和已发出的命令不因内部面板切换中断；远端主动断开和网络中断仍按真实状态显示。

本轮支持同一详情工作区内保留一份终端连接。跨服务器／跨页面后台保活、分屏、多终端会话不在本轮范围内。

### 3.4 配置

配置作为详情侧栏的一个入口。右侧面板标题为“配置”，内部按栏目切换，内置“基础配置”“软件策略”，插件可增加“容器设置”等栏目。栏目较多时使用可滚动的栏目选择控件，不再嵌套另一条完整宽侧栏。

| 栏目 | 内容与保存方式 |
| --- | --- |
| 基础配置 | 名称、区域、地址／端口／用户／认证、声明系统等；复用现有表单校验、连接测试和系统识别流程 |
| 分组／类型调整 | 基础配置内提供入口，使用现有移动预检和确认流程；普通保存不能直接改类型或绕过软件冲突检查 |
| 软件策略 | 是否自动安装缺失的必要软件、逐软件版本要求与自动检测升级偏好；复用现有策略接口 |
| 危险操作 | 基础配置底部保留删除服务器的明确入口，沿用任务互斥与历史保留规则 |
| 插件栏目 | 插件提供自定义 React 内容、配置定义和宿主校验；服务器管理提供统一读取／保存和冲突反馈 |

每个栏目独立保存，显示修改中、保存中、成功、校验失败、版本冲突等状态。不做一个容易出现部分成功的跨插件“保存全部”。离开有未保存修改的栏目时提供保存／放弃／留在当前页；后台观察刷新不会覆盖草稿。

首次登记仍使用登记表单；已有服务器的“编辑”入口指向配置内的基础栏目。组件可以复用，但不把整个带返回跳转的登记页面直接塞入配置。

## 4. 工作区状态与数据加载

`ServersPage` 负责选择实例列表、登记表单或详情工作区；详情工作区统一管理 `serverId`、`panelKey`、`settingsKey` 和各面板查询状态。终端不再是绕开工作区的顶层屏幕。

建议新增 `ServerWorkspace`，并将当前 `ServerDetail` 收敛为基础信息面板。工作区共享一份基础服务器资源，面板通过上下文读取，不重复开启多份基础轮询。

1. 基础状态使用现有可取消资源加载方式；请求完成后再安排下一轮，避免慢请求重叠。
2. 任务报告、插件业务列表只在面板激活时加载和轮询；离开时取消请求、计时器和观察器。
3. 表单草稿与筛选状态保存在工作区状态中，普通面板资源随卸载释放。终端连接与有界输出缓冲由工作区会话控制器持有，面板隐藏只释放视图事件和尺寸观察；退出工作区时才结束会话，不靠永久挂载所有面板维持状态。
4. 服务器 ID 是资源和组件实例边界。旧服务器的迟到响应不能写入新服务器页面；切换期间不能沿用旧数据作为当前数据。
5. 当前扩展被移除、不再适用或服务器已删除时，退出对应内容并给出原因。可用服务器回到基础详情，已删除服务器回到列表。
6. 语言切换只更新标题、标签和错误说明，不改变面板键、服务器身份和表单草稿。

## 5. 详情面板扩展契约

以下为拟新增的公开契约，当前代码尚不提供。具体类型定义放在 `shared/contracts/`，通过正式包导出；实现阶段同步更新契约版本校验和示例，不能把新字段直接传给当前版本并假设生效。

### 5.1 宿主定义与客户端渲染分工

服务器管理增加 `registerServerExtensions()` 注册入口，登记当前插件拥有的面板描述、配置描述、只读查询和巡检贡献。它返回与现有注册方式一致的 `ready/dispose` 句柄，归属于调用插件的 Cordis 生命周期。依赖某类型的扩展在类型注册成功后才发布；扩展定义整体校验失败时不发布半份目录。

| 描述字段 | 约束 |
| --- | --- |
| `owner` | 来源插件包名，由宿主按调用上下文核对，不由浏览器指定归属 |
| `key` | 插件内稳定键，完整身份为 `owner/key`；核心键保留，重复贡献报错 |
| `name` | 至少中文和英文；仅影响展示，不参与业务身份和执行修订 |
| `order` | 同一扩展区域内的排序值；同值按完整键排序 |
| `appliesTo` | 声明式类型键、操作系统等适用条件；省略类型限制可服务所有服务器 |
| `queries` | 该插件自定义面板需要的只读数据查询；输入与输出边界均校验 |

适用条件用于确定“这类服务器是否有这个功能”，不能把“Docker 正好已安装”当作入口存在条件；否则安装失败时用户反而找不到诊断面板。实时可用性在面板内说明。

目录展示根据服务器声明的类型和系统判断；OS 尚未核验或不匹配时保留适用面板及诊断说明。真正运行检查和变更时，另外核对当前探测系统、支持范围和配置修订，不能把入口可见当成执行许可。

基础接口返回当前服务器可用扩展目录，包含稳定键、双语名称、排序、提供者和可用状态。客户端只渲染当前宿主目录允许的贡献。已有宿主描述但客户端资源加载失败时显示明确的不可用占位与重试，不把加载失败解释成该服务器没有此功能。

### 5.2 使用现有槽承载组件

服务器实例页面声明两个 root、keyed 子槽：

| 槽 | 用途 |
| --- | --- |
| `server-management.detail.panel` | 详情工作区右侧自定义面板 |
| `server-management.settings.section` | “配置”面板内自定义栏目 |

贡献插件通过 `ctx.slots.inject()` 等待槽出现，再按完整贡献键注册组件；外壳通过 `renderSlot(..., { entryKey })` 渲染选中的贡献。槽随服务器管理客户端卸载撤回，贡献者随自身卸载清理。

公开注册辅助函数固定贡献键和默认优先级；外壳订阅原始槽账本，发现同键多项登记时将该扩展标记为冲突，不交给槽优先级选择一个覆盖者。内置面板由工作区直接选择，不暴露可被插件占用的扩展键。

不要给 `slots.register()` 塞任意 `visible/serverTypes/settingsSchema` 字段，再假设 `entries()` 会返回它们。已核对当前 Harness 槽账本只保留固定登记字段。适用条件和配置 schema 保存在上述宿主扩展目录，槽只负责定位组件和传递 owner props。

组件获得的公共上下文建议包括：当前服务器 ID、去除凭据的基础服务器视图、当前语言、刷新基础数据、跳转任务报告、切换详情面板／配置栏目，以及当前扩展的受约束 API 客户端。配置栏目额外获得草稿、校验错误、保存状态及修改通知。

客户端不接收 SSH 私钥、口令、密文、数据库连接、宿主脚本路径或任意 SSH 执行函数。自定义组件通过服务器管理的公共接口请求已登记能力；不能导入兄弟插件的私有源码。

每个扩展面板和配置栏目有独立错误边界。单个组件渲染异常不应使整个服务器工作区失效；宿主错误使用稳定代码及参数，提供者名称和错误展示信息有可持久化的双语快照。

### 5.3 宿主请求边界

建议统一使用服务器管理的鉴权入口分派扩展请求，例如：

- `GET /console-api/servers/:id/extensions`：当前服务器的扩展目录。
- `GET/PUT /console-api/servers/:id/extension-settings?key=...`：单个配置栏目的当前值／条件保存。
- `GET /console-api/servers/:id/extension-data?key=...&query=...`：已登记的只读查询，支持各查询声明的分页参数。
- `POST /console-api/servers/:id/extension-inspections?key=...`：排队执行已登记的只读检查。

完整键通过标准 URL 编码传输。路径名称是草案，重要的是所有入口复用当前控制台会话校验、服务器存在性和请求大小限制，并在服务端再次检查提供者、适用条件和配置修订。当前系统的控制台鉴权不等于已具备多用户服务器 ACL，本次不虚构新增权限体系。

只读 GET 读取持久化观察，不建立 SSH、不安装软件。手工刷新通过 POST 排队。插件的查询和结果 repository 属于插件；核心负责鉴权、分派和稳定错误响应，避免插件复制另一套服务器认证和凭据处理。

## 6. 配置扩展：可编辑、可持久化、可校验

仅能在配置页画组件不算完成配置扩展。每个栏目必须同时定义宿主数据契约：

- 完整键、双语名称、适用条件、schema 版本、默认值。
- 宿主输入 schema／校验器，以及可读字段和保存方式。
- 对执行的影响：只影响展示／只读观察，还是会影响远端变更计划。
- 如有敏感配置，声明敏感字段及单独的替换／清除语义。

建议由核心提供 `server_extension_settings` 持久化，以 `(server_id, extension_key)` 唯一：`schema_version`、`revision`、`value`、`updated_at`。小型插件配置使用经过校验的 JSONB；观测清单、任务与历史不塞进该表。

读取返回有效配置、默认值来源、schema 版本、配置修订和是否可编辑。尚未保存时可按默认值工作，读请求不隐式写库。保存需带预期修订；首次写入也需条件插入，避免两个页面同时创建时互相覆盖。冲突返回当前修订，页面提供重新加载／比较，不能静默覆盖。

schema 版本不兼容时，必须运行提供者明确声明的转换或提示重置，不能把旧 JSON 强转为新类型。未知字段、非法值和不适用栏目由宿主拒绝。JSONB 只提供存储形态，不替代校验。

首个容器配置只有非敏感开关；将来有 token 等字段时，明文不进入普通配置 JSON／读接口，使用现有密文能力和显式更新语义，返回只包含是否已设置。

影响和并发规则：

1. 容器清单采集开关改变栏目自己的修订，不使已经确认的软件升级计划失效。
2. 地址、认证、系统、分组、类型和软件范围继续遵循已有配置修订与任务互斥规则。
3. 将来会改变执行参数的插件配置，必须把相关栏目修订加入计划摘要和执行前复核。只改无关 UI 配置不应阻塞所有任务。
4. 保存本地管理配置不等于修改远端服务。需要写远端配置、安装、升级或重启的扩展，应走显式预检／确认／任务流程；首版容器设置不包含 Docker daemon 配置编辑。
5. 插件卸载保留配置记录，停止读取它来授权执行；重新启用后按当前 schema 验证。服务器删除时清理其当前配置，任务历史仍按现有身份快照保留。

## 7. 公共类型目录：去掉“两种内置类型”的假设

现有插件类型通常通过系统组的显式类型列表接入。独立容器类型必须能进入普通用户分组，因此需要补充公共类型目录，而不是为此强制用户搬到容器专属分组。

用户已确认下表的开放范围：普通用户分组、未分组和继承公共目录的系统分组均可选择容器类型，登记默认仍为空置；系统分组显式限定类型时继续遵循该组定义。

建议在定义包中增加显式 `publicTypes` 贡献，每项包含本包已声明的类型引用和排序值，注册时与类型定义一同原子发布。进入公共目录不改变登记默认值。未贡献该字段的插件类型仅通过显式系统分组引用使用。

| 分组情况 | 类型来源 | 默认选择 |
| --- | --- | --- |
| 用户分组／未分组 | 空置类型 + 当前可用插件的公共类型贡献 | 空置 |
| 系统分组省略 `types` | 动态继承同一公共目录 | 空置，或该组明确声明且有效的默认值 |
| 系统分组显式设置 `types` | 严格采用该列表，不自动注入容器类型 | 该组合法默认值 |

公共目录中先列空置，再按贡献排序和稳定键排列。操作系统过滤仍在前后端同时执行。容器类型初期继承当前配方已支持的 Ubuntu／Debian 范围；Windows Server 和不受支持的“其他”系统不能因改名就获得 Docker 安装能力。

公共类型增减要更新目录修订并使登记表单重新读取。用户已选类型消失时提示不可用并要求重新选择，不静默改为空置。公共目录的继承不是对所有贡献插件的硬依赖；卸载容器插件不应使普通分组和空置类型整体失效。显式引用其他插件类型的系统组继续执行真实依赖校验。

类型的解析、任务租约、移组、登记、编辑和删除用户分组统一使用同一目录判断。删除用户分组时，逐台判断移到未分组后类型是否仍允许及现有任务／系统约束；不能再写 `type === vacant || type === general`。需要改变类型或软件的情况进入现有预检流程。

核心不保留 `GENERAL_TYPE`、`builtin/general` 的运行时别名，也不按中文名称识别类型。正式新身份建议如下：

| 定义 | 完整键 |
| --- | --- |
| 容器类型 | `@smp/console-server-containers/container` |
| Docker 软件 | `@smp/console-server-containers/docker-engine` |
| Compose 软件 | `@smp/console-server-containers/docker-compose` |
| 配方 | `@smp/console-server-containers/docker-apt`、`@smp/console-server-containers/compose-apt` |
| 详情面板 | `@smp/console-server-containers/containers` |
| 配置栏目 | `@smp/console-server-containers/settings` |
| 清单巡检 | `@smp/console-server-containers/inventory` |

软件身份也一并迁出 `builtin/`，避免类型看似独立、Docker 仍靠核心特例才能运行。

## 8. 容器插件的职责与配置示例

容器插件通过公开定义接口登记类型、Docker／Compose 软件和配方，通过扩展接口登记容器面板、容器设置、清单查询和只读巡检。

| 核心服务器管理保留 | 容器插件负责 |
| --- | --- |
| 服务器、分组、凭据引用、OS 核验、主机指标、终端 | 容器类型与国际化名称 |
| 通用软件定义解析、版本规则、计划、队列、SSH 连接管理、恢复和升级调度 | Docker／Compose 软件定义、产品版本处理、apt 配方和依赖声明 |
| 基础详情、任务报告、配置外壳、扩展目录 | 容器清单面板、查询、展示、容器配置栏目 |
| 通用巡检调度、任务互斥、观察状态、汇总报告 | Docker 权限选择、容器清单采集、清单解析与专属 repository |
| 通用软件观察存储 | 容器清单业务存储 |

“容器”面板展示名称、镜像、状态、端口等现有字段，提供手动刷新、上次成功采集时间、当前检查状态和分页查询。采集失败时保留上次成功清单并明确标为历史观察；未检测、不适用、已关闭、失败、成功但为空必须区分。

“容器设置”首版提供“自动采集容器清单”开关，默认开启，沿用核心巡检周期。用户已确认：关闭后只停止该插件的周期清单采集，手动刷新仍可用，Docker／Compose 作为必要软件的健康检测继续执行。此开关不改变自动检测升级偏好。

仅选择容器类型的服务器默认适用这两个栏目。空置服务器即使碰巧安装 Docker，也不会被自动改类型或开始容器巡检。其他插件的类型如希望复用容器面板，需要后续通过明确的贡献引用／适用条件声明接入，不能通过名称或猜测已安装软件隐式匹配。

容器插件首版复用当前受控安装和只读权限行为：只读操作先尝试 SSH 用户权限，必要时使用已有 `sudo -n`；整轮使用选定的 Docker 上下文。安装、替换和升级继续经过通用计划，保留精确包、校验、失败实际变化与恢复语义。搬迁时修正配方中对 `builtin/docker-engine` 等旧键的判断，防止新键被错误识别成 Compose。

本轮用清单面板和采集配置验证扩展闭环。容器启停、部署编排、远端 Docker daemon 配置、容器终端等属于后续能力，不作为本轮插件化的隐含交付。

## 9. 巡检扩展与任务报告

仅移动前端容器表格不能完成拆分。核心 `inspectJob()` 应执行通用连接／系统／必要软件检查，再调用当前服务器适用且已启用的巡检贡献；不包含 Docker 名称、命令或容器表操作。

巡检贡献至少声明：提供者与键、适用条件、只读脚本及内容修订、超时／输出限制、结果校验、当前配置依赖，以及经核心封装的结果写入回调。

执行步骤：

1. 核心领取既有巡检任务，复核服务器配置、操作系统和当前提供者，取得相关定义／扩展租约。
2. 按当前设置选择巡检项；没有容器插件、不是容器类型或关闭周期采集时，不执行容器命令。手动清单刷新仅选择指定扩展检查项，仍执行通用连接、系统核验和修订检查。
3. 核心拥有 SSH 会话、超时、取消与输出脱敏；注册脚本接收结构化输入，不接收来自浏览器的任意 shell 命令。
4. 校验结果后，在执行令牌与相关配置修订仍有效的事务内落库。插件回调接收本次事务连接，只写自身业务数据，不自开事务或越过提交顺序。
5. 单项失败转换为带提供者、检查项、稳定代码和可读说明的结果，不丢失已取得的其他事实。SSH 已连通但容器读取失败，不改写为“断开”。
6. 同一轮巡检只记一次周期汇总计数；失败详情可列出多个检查项。手动刷新作为一次显式任务展示，周期成功仍只进入小时汇总。

巡检使用现有服务器任务串行机制，容器插件不另开周期 SSH 定时器与升级执行抢占。同一轮必要软件检测和容器清单采集可以复用核心会话，但两者有独立结果语义；容器列表读取不能把未验证的软件写成“健康”。

扩展巡检继续使用通用任务用途 `inspect`，请求快照显式记录触发来源（手动／周期）、贡献键、所需配置与提供者修订。任务报告按触发来源决定是否汇总，不能继续仅凭固定 action 名判断周期任务。查询筛选和结果 DTO 同步支持贡献身份；未知或已卸载提供者使用保存的文本快照展示，不能因缺少其前端代码而无法打开历史。

通用扩展观察可参与“需关注”的原因聚合，包含提供者与检查项，不能向核心状态模型新增 Docker 专属状态。关闭采集后旧错误退出当前告警判断，历史报告继续保留；当前数据标记为关闭／陈旧，不改写为新的成功观察。

只读配置变化或类型变化使旧检查结果过时时，迟到结果不覆盖新的观察。定义卸载后不再领取新检查；已接受任务依托租约完成有界检查和最终落库，再释放会话与定义。

## 10. 数据库与模型归属

沿用已完成的业务分层：业务 SQL 在各模块的 `persistence/`；PostgreSQL 连接池和迁移执行仍由数据库插件负责。独立插件不等于另建数据库或私自执行 DDL。

| 数据 | 归属与调整 |
| --- | --- |
| `servers/server_runtime` | 核心；保留基础配置和通用运行事实 |
| `server_software_observations/server_software_policies` | 核心通用存储；使用插件软件完整键，不增加 Docker 专属列 |
| `server_extension_settings`（新增） | 核心；每台服务器每个栏目一份有 schema 版本及修订的配置 |
| `server_extension_observations`（新增） | 核心；每台服务器每个巡检贡献的当前状态、错误、检查／成功时间、配置与提供者修订；不存整张容器清单 |
| `server_containers` | 业务归属移交容器插件，可沿用现有表名；核心不再读写它，查询和分页在插件 repository 内完成 |
| `server_container_scans` | 由通用扩展观察替代，实施时处理当前观察并移除专属扫描结构 |
| 任务、步骤、小时汇总、计划 | 继续使用核心表；扩展结果带提供者／贡献键和展示快照，避免重复建一套任务历史 |

扩展观察与容器清单更新必须同事务提交；成功后才替换清单，失败保留最近成功数据。外键保证删除服务器时清理当前配置／观察／清单，任务历史按 `server_identity` 与快照保留。

核心 `ServerDto` 移除容器字段。容器插件提供独立 DTO；基础详情不会为了显示地址和状态查询整个容器清单。配置、基础观察、容器观察的修订互相区分，普通采集不会把所有用户确认作废。

历史上允许破坏兼容，不代表当前测试服务器和任务已经为空。实施时检查实际记录并采用一次性转换：当前 `builtin/general` 登记与软件策略／当前观察改用新提供者键；旧建议失效并重新检测，未开始的旧计划要求重新预检。已开始或恢复中的操作先有序收尾，不能转换其执行身份。历史任务快照保留原事实和名称，不伪装成由新插件执行。

该转换属于一次性开发数据处理，不在长期运行代码中保留旧键分支。若实施时采用测试数据重置，应限定服务器相关记录和依赖范围，明确实际清理内容。本次设计不执行转换或删除数据。

## 11. 生命周期、卸载与重载

扩展注册、目录、配置服务和任务资源都属于单次 Cordis `apply`，遵循现有定义注册的所有权和租约规则。

1. 卸载开始即停止接受该提供者的新查询、保存、巡检和软件变更，前端扩展目录同步撤回。
2. 等待已接受的请求／检查／执行收尾。只读检查可有界取消；已开始修改软件的任务继续按现有执行／恢复规则结束，不能强杀包管理器。
3. 最终结果写完后，再释放插件持久化依赖、脚本、SSH 和槽登记；不能让 repository 使用的服务先被关闭。
4. 已选容器类型的服务器在插件不可用时保留原类型身份，显示“类型提供者不可用”，不偷偷改为空置。基础资料、任务报告及独立 SSH 终端仍可使用。
5. 配置和历史观察保留，重新启用时按稳定键与 schema 校验恢复；缓存不能授权执行已经撤回的脚本。
6. 当前插件面板退出后返回基础详情；未保存的插件草稿不能发送给卸载后的接口。组件异常、客户端资源失败与宿主卸载分别给出原因。

同键的重复注册不能靠优先级覆盖，重载不得产生重复侧栏入口、周期任务或监听。翻译改动不改变执行修订，配方／检查逻辑改动则必须改变相应修订。


插件只依赖正式包的公开导出。面向客户端的契约导出必须无 Node、数据库、SSH 等运行时依赖；不能从宿主入口引入整个实现。服务器管理不反向导入容器插件；容器插件不复制队列、密钥解密、通用软件计划或升级调度。

迁移 SQL 继续放在数据库插件的迁移目录，注明业务归属。容器表可以在插件未启用时存在，这不意味着后台巡检仍运行。

## 13. 实施顺序与验收

| 步骤 | 交付 | 完成判断 |
| --- | --- | --- |
| 1. 详情工作区 | 四个内置入口、独立任务面板、终端会话控制器、配置入口、状态保持 | 返回／切换服务器／分页／国际化正确；普通请求随面板清理，终端内部切换保持、退出工作区关闭 |
| 2. 扩展基础 | 面板和配置槽、宿主目录、配置校验与存储、公共类型目录、巡检注册与分派 | 使用隔离测试贡献验证，不能仅验证静态菜单能显示 |
| 3. 容器独立插件 | 迁出类型、软件、配方、清单、专属 SQL；贡献容器面板和配置；更新 CES 加载 | 核心独立运行只有空置类型；加载插件后容器能力完整恢复 |
| 4. 集成验收 | 一次性数据调整、旧特例清理、文档示例更新、故障与卸载验证 | 安装／移动／升级继续走现有通用路径，插件不需要核心专用分支 |

第 1 步与容器插件迁出的阶段可以分开提交，但完整需求在第 3、4 步完成后才交付。若中间版本临时隐藏原容器列表，应明确其属于阶段状态，不能将功能丢失记为最终完成。

验收清单：

- 普通服务器的当前类型展示改为“容器服务器 / Container server”，核心没有 `GENERAL_TYPE`、内置 Docker 软件、Docker 命令或容器查询特例。
- 空置、容器、系统组显式类型三类场景下，登记／编辑／移组／删除用户分组均使用统一目录，默认仍为空置。
- 首次进入终端前不建连接；同一服务器内切换所有面板并返回时，使用原会话、保留输出、不重复连接、不重放命令。终端隐藏期间不捕获其他面板的键盘输入。
- 退出详情工作区、切换服务器或主动断开时，终端连接关闭；连接身份变化后提示重新连接，核心卸载或连接建立期间退出也不遗留迟到会话。扩展插件卸载不关闭核心终端。
- 容器插件贡献独立面板和实际可保存配置；修改后刷新页面、重启服务可恢复配置，失效 schema 和并发保存有明确结果。
- 关闭容器清单自动采集后，该项周期命令停止；手动刷新和必要软件健康检测仍符合各自设置。
- 未加载插件、空置类型、OS 不匹配、不支持系统、Docker 未安装、权限不足、容器为空与服务器断开都有准确且不同的状态。
- 任务报告在服务端分页／筛选，插件周期成功按小时汇总，失败可定位到贡献者和检查项，历史不依赖插件在线才能阅读。
- 插件在当前面板打开、请求进行中、巡检进行中或软件变更进行中卸载时，入口、资源和任务均按上述生命周期收尾。
- 扩展键冲突、伪造提供者、不适用服务器、绕过 UI 直接请求配置／查询接口，由宿主拒绝；基础内置入口不可被覆盖。
- 使用一个独立测试贡献验证非容器面板和配置，且无需修改核心注册列表；测试贡献不随 CES 正式加载。
- 现有精确版本、替换确认、移动成功后提交、批量失败暂停、任务互斥和远端恢复测试继续通过。

验证分三层：纯规则与前后端契约检查；隔离 PostgreSQL schema、真实 Cordis 注册／卸载和 SSH 替身的集成测试；浏览器验证布局、切换、草稿、查询、语言和加载失败。远端软件安装／升级另用测试服务器按明确操作验证，不能以页面验收触发真实服务器变更。
