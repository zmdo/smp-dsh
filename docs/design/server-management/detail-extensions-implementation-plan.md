# 服务器详情扩展与容器插件：分步实施计划

日期：2026-10-20。状态：步骤 1 已完成；步骤 2～8 未开始。

依据：[服务器详情侧栏、配置扩展与容器服务器插件设计](detail-extensions-and-container-plugin.md)。设计确认已提交至 `ces/develop` 的 `f888e8e`；本计划细化实现顺序，不代表代码、数据库或运行配置已经调整。本文中的路径为当前入口或计划落点，新增路径将在对应步骤创建。

## 1. 交付目标与实施原则

最终应交付：

- 单台服务器详情工作区：服务器详情、任务报告、终端、配置，以及适用的插件面板。
- 插件可按服务器的稳定类型键声明专属面板和配置栏目。例如数据库类型插件的“数据库管理”仅在该类型实例内显示；容器类型提供“容器”面板。
- 同一服务器内部切换面板时保留终端会话；退出详情工作区、切换服务器或主动断开时关闭。
- 容器类型通过正式独立插件接入公共类型目录，核心只内置空置类型，登记默认仍为空置。
- 容器插件贡献类型、Docker／Compose 配方、容器清单、自动采集配置与巡检；自动采集默认开启，关闭后保留手动刷新和必要软件健康检测。
- 现有连接认证、系统核验、精确软件版本、移组预检、升级计划、任务互斥与恢复能力继续有效。

按下面八步顺序推进，每步完成后保留可构建、可验证的状态。新的行为及失败路径随步骤验证，纯组件移动不增加只镜像实现的测试。每步更新本计划的状态和验证记录，不能仅凭目录、接口或菜单已经出现就标为完成。

实施在 `ces/detail-extensions` 上进行，该分支从 `ces/develop` 的 `cf46e4f` 建出。步骤描述是后续开发安排；编写计划当次未创建分支、未执行迁移、未删除记录、未操作远端服务器。

## 3. 步骤 1：建立详情工作区，拆出任务报告

### 实现内容

1. 新增 `ServerWorkspace`，统一服务器标题、地址、状态、返回入口和局部侧栏。基础入口相对顺序为详情、任务报告、终端、配置；右侧标题随所选面板变化。
2. 收敛 `ServerDetail` 为基础信息和必要软件面板；把 `TaskHistory` 放入独立任务面板，复用现有服务端查询、分页和结果展示。
3. 扩展页面状态，保存服务器 ID、当前面板、任务筛选／页码及原实例列表视图。不同服务器的状态隔离，返回列表恢复原位置。
4. 将基础服务器请求提升到工作区，复用可取消资源加载方式；避免基础轮询重叠、旧服务器响应写入新页面、未激活任务面板继续轮询。
5. 保留当前操作入口。终端和编辑在本步骤先由局部导航连接到现有实现，分别在步骤 2、3 完成生命周期和内容拆分。

为避免中间版本丢失现有容器清单，将当前容器展示提取为临时内置“容器”面板，移出基础详情。它只复用旧数据和展示，不定义另一套扩展 API；步骤 7 必须删除此临时入口并改由正式插件注册。此时普通类型和后端容器巡检暂沿用旧实现，不能声称已完成插件化。

### 主要落点

- `client/servers/ServersPage.tsx`、`client/shared/server-page-state.ts`。
- 新增 `client/servers/workspace/`，整理 `detail/`、`tasks/` 和局部布局样式。
- 基础服务器资源、`TaskHistory` 的面板上下文和原列表状态。

### 验收与完成条件

- 点击服务器后出现局部侧栏；全局“服务器实例 / 服务器密钥 / 升级管理”导航及顶部样式保持现有职责。
- 基础详情不再直接展示容器表格或任务报告，相关信息可通过独立面板访问。
- 任务筛选、查询、分页、每页数量和小时汇总规则有效；切换面板不丢筛选，换服务器不串数据。
- 返回实例列表保留分组和页码；中英文、窄屏、长名称、加载失败均可正常使用。
- 浏览器确认布局；对状态隔离、迟到响应和任务查询范围做有意义的回归验证。

建议提交边界：工作区与任务面板作为一项可构建交付，不混入插件类型或数据库改造。

## 4. 步骤 2：终端会话随工作区存活

### 实现内容

1. 从 `ServerTerminal` 视图中抽出会话控制器，归属于一台服务器的详情工作区。只在首次进入终端时连接。
2. 内部面板切换只卸载终端视图，WebSocket／SSH 和有界输出缓冲继续存在；返回时复用原会话。
3. 隐藏终端释放键盘事件和尺寸观察；显示后通过本组件 ref 恢复尺寸，不使用全局 DOM 查询。
4. 实现明确的断开／重新连接状态。主动断开、网络失败后不因切回面板自动重连，不重放命令或输入。
5. 退出工作区、切换服务器、关闭页面、连接身份变化或核心插件卸载时关闭会话。检查全局页面切换是否保留组件，必要时根据工作区是否激活显式结束连接，不能只假设一定会触发 React 卸载。
6. 补齐宿主建立 SSH 期间客户端已经退出的清理路径；迟到连接、shell、事件与输出都不能逃出所属会话。

### 主要落点

- `client/servers/terminal/`、`client/servers/workspace/`。
- `host/remote/terminal.ts` 及其连接关闭路径。
- 当前服务器身份与连接身份修订的关联；普通指标刷新不重建终端。

### 验收与完成条件

- 进入终端前无连接；详情 → 终端 → 任务 → 配置 → 终端使用同一会话，输出连续。
- 其他面板输入不会发往终端；输出有上限，不无限增长。
- 切换服务器不会把输入或输出发给上一台机器；断开后可由用户明确重连。
- 工作区退出、连接建立期间退出、宿主拒绝、网络断开及核心卸载均释放资源；扩展插件卸载不关闭核心终端。
- 使用本地 SSH／WebSocket 替身验证连接次数和清理时序，再做浏览器交互验证，不用真实服务器命令证明会话保留。

建议单独提交终端生命周期改造，便于审查连接所有权。

## 5. 步骤 3：配置内置栏目与复用现有编辑能力

### 实现内容

1. 新增“配置”外壳，先接入“基础配置”“软件策略”两个内置栏目；为步骤 5 的插件栏目预留渲染位置。
2. 将现有编辑表单拆出可复用内容。首次登记仍是登记页面；已有服务器编辑在工作区内进行，避免整页跳转和重复标题。
3. 复用认证信息、连接测试、系统识别、已有密钥选项、字段联动和检测缓存。每个栏目只保存自己负责的字段，不用完整旧表单快照覆盖其他栏目的新值。
4. 分组和类型调整继续使用 `MoveServer` 的预检／确认流程；软件版本范围和自动检测偏好继续使用现有业务规则。
5. 每个栏目独立保存，保留草稿和未保存修改提示。保存失败留在当前栏目；后台观察刷新不重置草稿。
6. 将删除入口放入基础配置的明确操作区，继续遵循任务互斥和历史保留规则。

### 主要落点

- 新增 `client/servers/settings/`。
- `form/ServerForm.tsx`、`form/useServerForm.ts`、认证和系统字段组件。
- `detail/MoveServer.tsx`、软件策略组件和已有服务器编辑业务入口。

### 验收与完成条件

- 当前登记能力完整保留；编辑服务器可在配置内完成，地址／端口及用户字段布局符合已有要求。
- 只改一个栏目不会覆盖其他配置；栏目切换、保存失败和确认放弃草稿行为清楚。
- 修改类型无法绕过预检；关闭安装选项不能绕过已有软件版本冲突确认。
- 连接身份改变时步骤 2 的旧终端按规则关闭；修改名称或普通采集事实不会误断开。

步骤 1～3 完成后可验收四个基础入口，但尚未交付可用的插件扩展。

## 6. 步骤 4：公共类型目录与扩展契约

### 实现内容

1. 定稿并导出扩展契约：完整贡献键、所有者、双语名称、排序、类型／系统适用条件、面板描述、配置描述、只读查询、巡检定义及租约句柄。
2. 将类型的 `publicTypes` 贡献接入当前定义包，原子校验并发布。普通用户分组、未分组和继承目录的系统分组使用同一类型目录；显式类型列表仍严格遵守组定义。
3. 登记、移组、编辑、删除用户分组及执行租用统一调用目录解析，清除这些路径中的“两种内置类型”判断。
4. 实现 `registerServerExtensions()` 的所有权、引用校验、原子注册、目录修订和撤回机制。类型注册成功后才能发布依赖它的扩展。
5. 明确公共数据 DTO 和宿主运行时回调边界；客户端契约导出不得引入数据库、SSH 或 Node 运行时。
6. 确定契约版本和错误码，更新设计中的草案说明。旧版本、新字段和不支持能力都应明确处理，不能静默忽略。

本步骤先让目录和契约具备扩展能力；旧普通类型及内置配方仍暂留，待步骤 7 与当前数据一次切换。公共目录变化不能把所有继承它的分组变成对全部插件的硬依赖。

### 主要落点

- `shared/contracts/`、公开包导出及架构约束。
- `host/definitions/registry.ts`、`resolver.ts`、`validation.ts`、相关视图。
- `host/groups/service.ts`、目录读取与表单目录刷新。
- 新增 `host/extensions/` 的目录和生命周期实现。

### 验收与完成条件

- 独立测试插件注册自定义类型后，可在普通用户分组选择，不要求创建系统分组；默认仍为空置。
- 显式限制类型的系统组不被公共类型自动扩充；系统范围继续限制实际可选项。
- 重名显示不影响稳定键；重复键、错误所有者、缺失引用、非法默认类型明确失败。
- 插件撤回后不能新建相关任务；已登记服务器保留原类型身份并显示不可用，其他公共类型仍可使用。
- 登记失败无半份目录，重载无重复贡献；依赖租约和卸载顺序通过真实 Cordis 测试验证。

测试贡献放在测试 fixtures，由测试装载，不加入正式 CES 运行配置。

## 7. 步骤 5：让自定义面板和配置真正可用

### 实现内容

1. 声明 `server-management.detail.panel`、`server-management.settings.section` 两个 root、keyed 槽。通过公开辅助接口登记组件，使用宿主目录决定名称、排序与适用性。
2. 实现当前服务器扩展目录与只读数据查询分派；服务端校验会话、服务器、提供者和适用条件。
3. 在工作区侧栏和配置栏目中接入动态贡献。按类型显示专属内容，不因软件尚未安装而隐藏诊断面板。
4. 提供独立错误边界、资源加载失败占位和键冲突检测；贡献消失时回到基础详情，不用槽优先级隐式覆盖。
5. 增加 `server_extension_settings` 迁移及 repository，实现 schema／默认值／版本校验、条件创建、带修订保存、独立栏目草稿和冲突反馈。
6. 区分观察配置与影响执行的配置修订；为后者提供计划绑定与复核接口。首个容器设置只需要非敏感的观察开关，未知敏感配置能力必须明确拒绝，不能先落成明文 JSON。

迁移沿用数据库插件的执行方式；业务 SQL 留在 `host/extensions/persistence/`。本步骤在隔离 schema 验证结构，再按后续开发的实际环境应用，不通过 GET 隐式建配置。

### 验收与完成条件

- 测试插件定义“数据库服务器”及“数据库管理”面板：只在该类型服务器上显示，其他类型和空置类型无该入口。
- 同一插件的专属配置栏目也按类型过滤；直接请求其他类型服务器的数据／配置接口会被拒绝。
- 类型变更成功后入口更新；变更尚未成功时仍按原类型显示，不能随预检目标提前切换。
- 配置保存、刷新、重启、双页面并发保存、schema 不兼容和非法字段均有确定结果。
- 中文／英文动态切换不改贡献身份；客户端组件失败不影响基础面板；卸载／重载不残留入口或轮询。

完成本步骤时，应已有一个通过正式契约接入的独立测试插件，而不是仅使用核心内嵌的假菜单证明扩展可用。

## 8. 步骤 6：巡检贡献接入核心任务体系

### 实现内容

1. 增加通用扩展观察存储 `server_extension_observations`，记录检查／成功时间、结果状态、错误和相关修订；业务清单仍由贡献插件存储。
2. 实现巡检注册、只读脚本快照、输出校验、提供者租约和结果提交回调。执行器拥有 SSH 和任务 fence，插件 callback 使用本次事务连接。
3. 在通用 `inspect` 任务中选择适用、已启用的检查项；手动检查指定贡献但仍经过连接、系统和修订校验。
4. 显式记录手动／周期来源、贡献身份及所需配置修订。更新任务查询过滤规则，周期成功按小时汇总，手动检查和失败结果独立可查。
5. 将失败原因纳入可读结果和统一状态；单项检查失败不抹去连接成功事实，清单失败保留最后成功观察。
6. 完成取消、插件撤回、配置变更、过期 fence 和迟到结果的处理。配置关闭后停止后续周期采集，已接受的只读工作有界收尾。

### 主要落点

- `host/extensions/`、`host/execution/handlers/inspect.ts`、队列与执行上下文。
- 通用观察持久化、`host/tasks/` 查询与报告 DTO、客户端任务结果展示。
- 数据库插件的新增迁移与隔离集成测试。

### 验收与完成条件

- 测试巡检复用核心队列和互斥，贡献插件不创建第二套周期 SSH 调度。
- 成功观察和业务清单同事务生效；结果写入失败不产生“清单已更新、状态仍是旧值”的半提交。
- 周期成功不刷屏；失败明确指出提供者和检查项，插件卸载后历史仍可阅读。
- 配置改变或提供者撤回后，旧结果不能覆盖当前观察；SSH 在线而扩展检查失败时显示需关注而非断开。

旧容器巡检在本步骤仍只有原执行路径；不要提前同时注册正式容器巡检，双路径切换统一放在步骤 7。

## 9. 步骤 7：完整迁出容器插件并统一切换

此步骤是功能和数据身份的切换点。容器插件、核心特例删除、迁移以及 CES 加载配置作为同一可运行交付，不能推送一个只有半边实现的运行版本。

### 7.1 创建正式容器插件

- 创建 `plugins/server-containers`，包名 `@smp/console-server-containers`，提供 manifest、Cordis patch、图标、中英文及宿主／客户端入口。
- 登记容器类型和公共类型贡献；Docker／Compose 软件、配方和依赖改为提供者命名空间的稳定键。
- 迁出 Docker 专属 apt 逻辑、版本解析、容器权限选择、清单解析与 repository，修正脚本中对旧 `builtin/` 软件键的判断。
- 使用步骤 5 的两个槽提供容器面板和容器设置；容器列表服务端查询／分页，配置开关默认开启。
- 使用步骤 6 的巡检贡献；手动刷新与周期采集复用核心执行机制。

### 7.2 去除核心特例

- 删除 `GENERAL_TYPE`、普通类型、内置 Docker／Compose 目录与配方。
- 核心观察服务和 DTO 去掉 `docker_version/compose_version/containers*`；必要软件表继续读取通用软件观察。
- 核心不再执行 Docker 命令或查询容器表；移除步骤 1 的临时内置容器面板。
- 容器插件不复制核心凭据、队列、软件计划、升级调度或恢复实现；核心不反向导入容器插件。

### 7.3 当前数据与启动切换

1. 核对当前登记、策略、观察、建议、计划及任务的实际记录，确定受影响键和运行任务；不沿用早期“没有服务器数据”的假设。
2. 先在隔离数据库分别验证空库安装和有测试记录的一次性转换。当前类型、策略和观察改用新键；旧建议失效，未开始的旧计划要求重新预检；历史报告保留原执行事实。
3. 已开始或恢复中的远端操作先有序收尾，再进行身份切换；不重写其操作 ID，也不把断连当作未执行。
4. 将 `server_container_scans` 当前状态转换到通用扩展观察，容器清单表移交插件业务代码。新增迁移编号按实施时仓库顺序确定。
5. 在受控停止旧工作进程后，按已验证顺序应用数据调整并加载匹配的核心和插件产物；避免旧巡检仍在写已经改变的结构。
6. CES 显式加载正式容器插件，临时测试贡献不加载。定义尚未就绪时，调度器等待／报告不可用，不凭缓存执行。

若后续开发选择重置测试数据，先明确服务器相关记录和依赖范围，并记录实际处理结果；长期代码仍不保留旧键兼容分支。本步骤不以真实服务器的软件安装或升级验证数据库转换。

### 验收与完成条件

- 核心单独启动：只有空置内置类型，服务器详情、任务和终端可用，无 Docker 清单巡检。
- 核心加容器插件：公共分组可选择容器类型，名称、必要软件、容器面板、配置和巡检完整工作。
- 空置服务器即使已有 Docker 也不自动出现容器面板／执行容器清单巡检。
- 容器类型上 Docker 缺失时仍显示面板及诊断；权限不足、未核验系统、空清单和已关闭状态分别展示。
- 关闭自动采集后周期清单命令停止；手动刷新、必要软件健康检测、升级检测偏好各自按规则工作。
- 卸载容器插件后保留登记身份、配置和历史；无新容器任务，基础终端仍可用，重载不重复登记。
- 通用安装、移动和升级通过插件配方完成，不需要恢复任何 Docker 核心特例。
