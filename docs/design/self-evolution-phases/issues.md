## 3. 逐项说明

### SE-PHASE-001：联网依赖与重建输入待验证

**原问题与处理决定**

初次评审时，[阶段方案](README.md) §3.3 同时要求“只依赖本项目打包的 Docker 镜像”、安装 Docker 和断网完成全流程，且未定义模型服务访问方式。

2026-10-24 用户明确要求保留外网。阶段方案已改为联网重建，允许在线安装 Docker 和依赖、拉取镜像及连接外部模型 API；不再要求完整离线包或部署内网模型。原离线边界问题已通过需求澄清消除，本项继续跟踪具体依赖来源、版本和可重建性的验证。

**影响**

已有镜像能够启动，不等于干净环境能构建下一版 CES。即使具备外网，未记录的本机依赖、不可访问的下载源或缺失的模型配置仍会阻断重建和自演进。

**处理建议**

- 明确宿主前置条件，记录 Docker/containerd、Compose、Buildx 及系统依赖的在线安装方式和版本。
- 按实际构建链补齐下载来源及版本：构建基础镜像、所需 BuildKit 镜像、Node/npm/dsh 依赖、自动化测试所需浏览器及系统依赖、CoreDNS 镜像与配置、内部 CA 和信任配置。
- 记录模型 API 地址、凭据注入方式及网络要求，验证 CES 可实际调用；凭据不写入 Git 或验证日志。
- 建立联网重建清单，记录平台、镜像 digest 或包校验信息、用途及获取方式；模型连接所需配置也应有可复现的设置步骤。

**关闭条件**

在有外网、空构建缓存和无隐式本机依赖的环境下，按清单完成部署、模型调用、新代码提交、镜像构建、B 测试和 C 发布。保存依赖来源、版本及执行结果；仅拉取已有 CES 镜像并启动不满足此条件。

### SE-PHASE-002：“已完成”声明缺少一致的验证证据

**依据**

[阶段方案](README.md) §2.5 将“buildspec 解析和执行验证”列为已完成，而 [OneDev 自动初始化验证](../ces-self-evolution-infrastructure/ONEDEV_BOOTSTRAP_VERIFICATION.md) §7 明确说明只验证了 Agent 在线，未执行真实构建任务。该报告使用独立 Compose 验证脚本，不能直接作为插件 recipe 端到端安装成功的证据。

[插件定义](../../../plugins/self-evolution/src/index.ts)已经注册三种服务器类型，但 `test`、`host` 的 `requirements` 仍为空。类型已注册不等于 B、C 的部署能力已完成。当前项目自动创建相关修改还位于未提交的 [stack.sh](../../../plugins/self-evolution/scripts/stack.sh) 中，且存在第 008 项问题。

**影响**

后续实施可能跳过未完成的前置验证，或误认为独立脚本验证已经覆盖插件安装路径。现有仓库证据不能支撑全部“已完成”声明；这也不等于断言仓库之外从未做过验证。

**处理建议**

将进展拆分为“定义已注册”“实现已编写”“独立脚本验证通过”“插件路径验证通过”“流水线真实执行通过”，为每项附上对应提交和验证记录。没有可核对证据的项标为待验证。

**关闭条件**

真实 Job 的记录包含代码提交、buildspec 版本、构建 ID、执行器、执行日志和结果；插件安装另有端到端记录。阶段方案与验证报告的状态一致，未提交改动不被当作已交付版本。

### SE-PHASE-003：进入条件、交付范围与退出门禁不一致

**依据**

[阶段方案](README.md) §6 仍要求进入 P1 前完成 `build/test/release` 和 SSH 部署；§7 的阶段一退出条件仅包含本机构建、插件测试、OneDev 和 Agent 可运行。§2.3 将发布和回滚脚本列为阶段一交付，§2.4 则以简单 Job 执行为验收重点。原先提前要求的 P3 离线包已取消，联网重建及恢复材料已归入进入 P3 前的准备工作。

**影响**

按 §6 执行仍会把 P2 的生产发布交付提前到 P1 之前；按 §7 执行又可能遗漏 §2.4 的真实 Job 验证。团队无法据此明确判断何时可以进入下一阶段。

**处理建议**

统一每阶段的进入条件、必须交付和退出证据，采用第 4 节的门禁分配建议。P3 联网重建和恢复材料可以提前准备，不作为启动 P1 的必要条件；生产发布能力应在 P2 使用前具备并验证。

P1 的构建输入还需明确承接[基础设施方案](../ces-self-evolution-infrastructure/README.md) §9 已列出的 CES 可分发运行包、依赖来源整理和空库初始化，避免“Job 能执行”替代“CES 能干净构建并运行”。

**关闭条件**

§2、§3、§6、§7 使用一致的门禁表，每项前置任务均有归属阶段和证据。验收顺序保持 P1 → P2 → P3；准备工作可并行，但不能跳过验收。

### SE-PHASE-004：Agent 布局和跨主机访问约定不一致

**依据**

[阶段方案](README.md) §3.1 仅在 A 下列出 Agent 和发布执行器，B 未列出构建 Agent；[基础设施方案](../ces-self-evolution-infrastructure/README.md) §6.1 则明确 B 使用 `ces-build-test`，A 使用 `ces-production-deploy`。

基础设施方案的入口表允许正式 CES 访问 B 的测试入口；[内网域名与网络方案](../ces-self-evolution-infrastructure/INTERNAL_DNS_AND_NETWORKS.md) §5 又整体禁止 `C → B`。

**影响**

Agent 布局歧义可能让构建落到 A。若严格禁止 C 访问 B，生产 CES 就无法按入口表直接开展候选接口或浏览器验证。

**处理建议**

- 统一 A 专用发布 Agent、B 构建测试 Agent 的部署与职责，Job 显式选择执行器。
- 明确验证路径：允许 C 访问 B 的测试 HTTPS 入口，继续隔离生产数据库和内部容器网络；或者全部验证在 B 执行，C 经 A 获取报告，并同步调整入口及流程描述。
- DNS、证书信任和必要连通性应在使用它们的阶段验证；阶段三负责正式运维配置，不能成为第一次验证这些依赖的时点。

**关闭条件**

三份文档中的主机布局和连接矩阵一致；实际 Job 日志可确认构建在 B、生产部署在 A；选定的候选验证路径通过端到端验证。

### SE-PHASE-005：生产替换与失败恢复验收过于笼统

**依据**

[阶段方案](README.md) §3.2 仅以“失败可回滚”概括 P2 恢复能力，备份与恢复又主要列在阶段三。[基础设施方案](../ces-self-evolution-infrastructure/README.md) §7.2、§8、§10 已要求独立发布记录、幂等、迁移兼容性和恢复演练，但这些条件未进入阶段门禁。

当前[数据库启动逻辑](../../../plugins/database/src/index.ts)会运行迁移，[迁移 runner](../../../plugins/database/src/migrate.ts)没有全局迁移锁或数据库降级执行器。因此退回旧镜像不能保证数据库也恢复到可用状态。

**影响**

正常替换成功不能证明自演进可靠。C 停止后发布中断、重复请求、数据库不兼容或数据未落盘，都可能使旧 CES 无法恢复；此时再到阶段三补恢复能力已经太晚。

**处理建议**

将下列验证纳入 P2，并在首次生产角色替换前具备必要备份和恢复条件：

- C 停止后，A 仍能独立完成部署、健康检查和恢复，并保存结果。
- 新镜像启动或健康检查失败时，能够恢复兼容的上一镜像。
- 重复发布请求、Agent 重启、SSH 中断不会导致并发替换或错误成功状态。
- 数据库变更有兼容性说明；不兼容迁移有独立恢复方案，状态不确定时保留数据并进入明确的维护状态。
- 会话、工作区、配置和密钥在升级与恢复后仍可使用，备份已经实际验证可恢复。

数据库备份恢复可能丢失备份后的写入，不能把“自动恢复备份且无损”作为默认承诺。阶段三可以完善持续备份、监控和运维制度，但基础恢复能力属于 P2 前置及验收内容。

**关闭条件**

保存正常发布、启动失败、连接中断、重复请求及兼容迁移回退的演练记录，关联发布 ID、镜像 digest、备份及恢复结果，并说明不可自动恢复场景的处理边界。

### SE-PHASE-006：用户验收、工具审批与 AI 自行验收混用

**依据**

[阶段方案](README.md) §2.5 使用“发布审批状态机”，§4.3 使用“生产发布有审批”，§7 又写“生产 CES 可自行提交、触发、验收并替换 C”。这些表述与该文 §5 的“发布必须经过用户验收”，以及[基础设施方案](../ces-self-evolution-infrastructure/README.md) §7.1 的单用户、完全访问语义不一致。

**影响**

实现时可能重新引入已取消的强审批，或者让模型把自动测试通过视为用户已验收，均偏离已确定的产品行为。

**处理建议**

统一为“CES 自动检查 → 用户验收指定候选 → 独立发布执行器部署”。保留候选、验收和发布状态管理，但明确验收主体是用户，AI 负责检查、说明和提交发布请求。

“完全访问”仍跳过工具层逐次权限审批；用户验收绑定提交、构建和镜像 digest，不增加多用户审核角色，不在流水线各步骤重复要求同一份验收。候选改变后，旧验收不能自动适用于新候选。

**关闭条件**

各文档统一使用上述语义，后续场景验证覆盖：完全访问下工具可执行；用户已验收的候选可发布；候选变化后不会复用旧验收；AI 自动检查不会自行生成用户验收记录。

### SE-PHASE-007：重建与恢复步骤待细化和验证

**原问题与当前状态**

初次评审时，[阶段方案](README.md) §3.3 将清除 A/B/C 后导入初始仓库、初始提交和 buildspec 称为“自动恢复”，未明确清理后的执行入口和材料保存位置。

联网方案修订已区分全新安装与指定备份恢复，并要求由外部引导、保留范围外的材料、仅清理隔离演练资源。具体主机清理清单、引导脚本和恢复操作步骤仍需补齐并验证；文档明确边界不等于已有可执行方案。

**影响**

若实际执行时 CES、仓库和引导材料仍在被清理范围内，流程将失去执行入口；使用未记录的残留缓存又可能使干净重建验证失真。若未独立演练备份恢复，还会漏验恢复现有加密数据所需的密钥和备份。

**处理建议**

- 明确 P2 的 C 是生产角色验证实例，P3 在隔离的 A/B/C 演练环境执行，不以清空真实生产数据作为验收步骤。
- 落实 A/B/C 之外的操作人或引导脚本作为初始执行方；仓库副本、校验材料、必要配置和恢复材料置于清理范围之外。
- 列出清理对象及保留的宿主前置条件，定义初始地址、DNS/信任引导和启动顺序：外部引导启动 A，再部署 B/C，最后由 C 接管自演进。
- 分开定义“全新安装”和“备份恢复”：前者导入初始化内容并生成新环境配置；后者恢复指定备份、原有必要密钥及业务数据，并验证连续性。

**关闭条件**

两类场景各有操作边界和成功证据。全新安装在有外网、清理范围明确、无隐式缓存条件下可重复；恢复演练验证指定恢复点的数据、配置和密钥可用。执行入口、仓库副本及重建和恢复材料在清理后仍可访问。

### SE-PHASE-008：工作区脚本的 `request` 名称覆盖阻断 recipe 路径

**依据**

此项仅针对评审时未提交的 [stack.sh](../../../plugins/self-evolution/scripts/stack.sh)。脚本第 9 行将输入 JSON 赋给 `request`，第 119 行又定义同名 HTTP 函数，覆盖输入变量；第 209 行 `resolve` 使用 `request.get('installed')`，第 219 行 `execute` 使用 `request['change']`。

评审通过隔离的名称绑定检查确认对应结果，未执行完整 recipe 或远端操作：

```text
request.get('installed') → AttributeError: 'function' object has no attribute 'get'
request['change'] → TypeError: 'function' object is not subscriptable
```

评审文件 SHA-256：

```text
d01cfa2f98d8fbcf28577e82fbc09980e68fd3486f589d3ab936977f26b84836
```

**影响**

当前工作区版本的 `resolve`、`execute` 路径会失败，影响共享该脚本的安装 recipe。不能据此宣称插件安装路径已验证可用；这是一项实现缺陷，不代表三阶段架构本身不可行。

**处理建议**

在后续代码修复中区分输入对象与 HTTP 请求函数的名称，并针对实际 `resolve`、`execute` 分支进行验证。本次仅记录，不修改该文件。

**关闭条件**

对应修复提交消除变量覆盖；两条受影响路径有针对性验证，插件实际安装另有结果记录。不能仅以脚本语法检查或 Agent 在线代替这些验证。

## 4. 阶段门禁修订建议

下表用于解决第 003 项，并承接其他问题的验收责任；尚未替代原方案。

| 阶段 | 应具备或完成的能力 | 退出证据 |
| --- | --- | --- |
| 阶段一 | 插件基础定义及安装路径可用；OneDev、项目、Agent 和最小 buildspec 就绪 | 本机构建与插件验证通过；真实最小 Job 执行成功 |
| P1 | 本机提交；B 从干净提交构建 CES；测试数据库可初始化；候选部署及访问可用 | 提交、构建、digest、B 部署和测试结果可追溯；用户可访问候选 |
