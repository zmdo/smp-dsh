# 生命周期

来源：`docs/cordis-tutorial/02-lifecycle-and-effects.md`，以及 `.agents/skills/cordis-styling-nitpicking/SKILL.md`。审查插件时只报告下面三条能够举出交错顺序和可见后果的问题。

纤维状态：`PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED`，加载失败进入 `FAILED`。`PENDING` 表示 `inject` 里的服务还没有。

`ctx.effect(fn)` 在加载时执行 `fn`，卸载时执行它返回的清理函数。`ctx.plugin()`、`ctx.on()` 的登记本身已经是 effect。Cordis 不管的资源（定时器、连接、监听、临时文件、子进程）必须放进 effect，并在清理函数里停干净。

## 禁止：模块级可变单例

一个进程里只有一份、身份来自模块加载、静态字段、全局符号或 `getInstance()` 的可变状态，要改成 Cordis 服务，或放进某次 `apply` 拥有的记录。不可变常量、冻结的纯表、无状态函数不在此列。

## 禁止：卸不掉的副作用

插件卸载后仍留着监听、登记、定时器、子纤维、进程、连接或订阅，就是缺陷。只 abort 或 kill、却不等它们结束，也算，只要清理函数可能在工作停止前返回。

有意写下的持久数据不必回滚。做这些事时用过的临时资源仍然要有所有者。

## 禁止：使用方还没结束，依赖先被拆掉

清理过程里还要调用的服务、还要送达的事件，在使用方结束前必须保持可用。这包括最后一次写完持久结果。

当前 Cordis 卸纤维时，兄弟清理函数并发开始。服务撤回会等仍登记在案的依赖纤维，但兄弟资源可能已经在关。只加 `inject`、只把登记顺序倒过来、只留着一个服务引用，都不能消除这个交错。

正确顺序：停止接收新工作，等已经接收的使用方结束，再释放资源。用一个 `ctx.effect(function* () { ... })` 把清理串起来时，要 `yield` 登记函数返回的那个清理函数本身，不要再包一层。服务用 `yield ctx.provide(name, service)` 放在最后发布，这样反向卸载会先撤回服务，再释放前面的资源。

插件函数顶层的 `yield` 不是这条顺序的保证。生成器 effect 只管它自己收集到的清理函数。
